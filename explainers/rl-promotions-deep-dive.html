RL for Promotions — the Full Deep Dive

Added 2026-09-02

You framed discount promotions as a reinforcement learning problem, built a data-driven simulator from production logs, trained tabular Q-learning and DQN agents at scale, deployed the policy in a live A/B on ~2.2M users — and the result came out flat. This page rebuilds the whole thing from fundamentals up, with the real code and the real autopsy, so an RL person can go as deep as they want and you don't run out of floor.

Part 0 — RL fundamentals, rebuilt from rust

Everything in RL is one loop: an agent observes a state, picks an action, and the environment returns a reward and a next state. Here the agent is the promo engine; the environment is the user (plus the cricket calendar).

Agent (promo policy π) — sees state st, picks action at (a discount tier)
↓  at
Environment (the user + match calendar) — user reacts: plays or doesn't, uses the discount or doesn't
↓  rt, st+1
Loop repeats for T = 10 days (one episode)

The MDP

A Markov Decision Process is the 5-tuple (S, A, P, R, γ): states, actions, transition kernel P(s′ | s, a), reward function R(s, a, s′), and discount factor γ. The Markov property is the load-bearing assumption: the current state contains everything needed to predict what happens next — history beyond s adds nothing. (Foreshadowing: our state didn't, and that's half the autopsy.)

The agent maximizes the return — cumulative discounted reward:

Gt = rt+1 + γ·rt+2 + γ²·rt+3 + … = Σk≥0 γk rt+k+1

The project used γ = 1: with a fixed 10-step horizon the return is bounded, and every day of retention counts equally. γ < 1 is what you need for infinite horizons (convergence) or when sooner genuinely beats later.

Value functions and the Bellman equations

A policy π maps states to actions. Its action-value function Qπ(s, a) = E[Gt | st=s, at=a, then follow π]. The optimal Q* satisfies the Bellman optimality equation:

Q*(s, a) = Es′[ r + γ · maxa′ Q*(s′, a′) ]

Read it as: the value of doing a in s = immediate reward + the value of behaving optimally afterwards. If you know Q*, the optimal policy is trivial — π*(s) = argmaxa Q*(s, a). All of Q-learning is "estimate Q* from samples."

Q-learning: off-policy TD control

Q-learning turns the Bellman optimality equation into an incremental update. After experiencing (s, a, r, s′):

Q(s,a) ← Q(s,a) + α · [ r + γ · maxa′ Q(s′,a′) − Q(s,a) ]

The bracketed term is the TD error: (target − current estimate). Three things to be able to say fluently:

  • Off-policy: the target uses maxa′ — the greedy action — regardless of what the behavior policy (ε-greedy) actually does next. You learn about the optimal policy while behaving exploratorily. SARSA, by contrast, plugs in the action actually taken (on-policy).
  • ε-greedy: with probability ε act randomly, else act greedily. Decay ε over training (we went 1.0 → 0.01) so early exploration gives way to exploitation.
  • Convergence: tabular Q-learning converges to Q* if every (s,a) pair is visited infinitely often and the learning rate satisfies the Robbins-Monro conditions. Finite state space + enough episodes ≈ good enough in practice.

DQN: when the table gets too big

Tabular Q-learning stores one number per (s,a). When states are continuous or too numerous you replace the table with a network Qθ(s,a) and minimize the squared TD error:

L(θ) = E(s,a,r,s′)∼D[ ( r + γ · maxa′ Qθ⁻(s′,a′) − Qθ(s,a) )² ]

Naively this diverges — bootstrapped targets + function approximation + off-policy data is Sutton's "deadly triad." DQN's two stabilizers, both in our implementation:

  • Experience replay (D): store transitions in a buffer, train on random minibatches. Breaks the temporal correlation between consecutive samples and reuses data.
  • Target network (θ⁻): compute targets with a frozen copy of the network, synced every N steps (we used 100). Otherwise you're regressing toward a target that moves every gradient step.

One more line worth having ready: the max operator makes Q-learning overestimate (max of noisy estimates ≥ estimate of max — Jensen). Double DQN fixes it by selecting the argmax with the online net but evaluating it with the target net.

Part 1 — the problem

Dream11 hands out discount promotions to bring lapsed users back. The incumbent system (Pacman) used a supervised churn model plus a static "retention grid": given (churn bucket, days inactive), look up a discount. It works, but it's myopic — every day is decided independently, with no notion of sequencing, saving budget for big match days, or long-run effects.

The RL framing: maximize cumulative DAU over the horizon, under a budget:

maxπ Σt=1..T Σi r(sit, π(sit))   s.t.   Σt Σi c(sit, π(sit)) ≤ B

Why not a contextual bandit? Because actions have sequential effects: a 100% discount today changes tomorrow's state (and may train the user to wait for discounts). Bandits optimize immediate reward per decision; the whole point here is long-horizon credit. Knapsack-bandit variants were considered and rejected — they assume i.i.d. rewards per pull, which promo responses violate.

The cast: agent = promo engine · environment = user + match calendar · action = discount tier · reward = "did they come back, and how much did it cost us" · episode = 10 days.

Supply tiers encode the cricket calendar: t1 = IPL / India World Cup matches, t2 = other India internationals, t3 = everything else. Dims 4–8 are forward-looking: they let the agent learn things like "don't burn a 100% discount on a t3 Tuesday when an IPL match lands Friday." That's the sequential structure a bandit can't see. The supply sequence is exogenous — sampled from the real match calendar, not affected by actions.

Action: 6 discount tiers

Discrete(6) → {no promo, 10%, 25%, 50%, 75%, 100% discount}, each capped at a fixed rupee value. Small deliberately: every action needed enough historical data to estimate its effects (see the simulator's masking rule).

Horizon and discounting

Episodes are 10 timesteps (1 step = 1 day), γ = 1. Finite horizon does the truncation that γ < 1 normally does; undiscounted means day-9 retention is worth as much as day-1. The strategic ambition was a ~60-day horizon; 10 days is what the data could support.

Part 3 — reward shaping (where it went wrong first)

The reward has to encode a dual objective in one scalar: reward retention, penalize spend. The design: when a user is active at t, reward depends on how much promo cash (cb, cashback used) it took relative to their contest entry amount (cea):

R = a · e−γr · (cb/cea) + b,   a = (α−1)/(e−γr−1),   b = 1−a

The a, b algebra pins two endpoints: R(0) = 1 (user played, cost you nothing — full reward) and R(1) = α (user played entirely on your money — reward α). Inactive users get 0. So α is literally "how much credit do I give a fully-bought retention day," and γr sets how fast credit decays as subsidy rises.

The sweep covered a 13 × 20 grid of (α, γr) — 260 reward shapes, each defining a different MDP. Findings: lower α → less retention and less spend but better retention-per-rupee; higher γr cut spend without hurting retention much. Set α high and flat (α = 0.5, γr = 0.5) and look at how little a 100%-subsidized day is punished — that's the shape that taught the agent to overspend.

Design principles that made it into the docs — all standard, all learned the hard way: keep the reward smooth so there's gradient signal; avoid large negative regions (an agent can learn to rush to episode-end to stop accumulating negatives); make sure the state can distinguish situations the reward treats differently. And the meta-lesson, verbatim from the retro: "getting the reward even slightly wrong will lead the agent to learn unexpected behavior, as we have learned the hard way." That's a reward-hacking story you own — same failure family as under-penalized length in RLHF reward models.

Part 4 — the simulator: an empirical MDP from logs

You can't do ε-greedy exploration on paying users. So the MDP was estimated from ~7 months of production promo logs and the agent trained inside it. Everything is empirical — no hand-authored dynamics:

Production logs — per user-day: state (days_inactive, churn_bucket), promo shown (action), what happened next
↓ PySpark, group by (state, action, supply-context)
Transition table — P(s′ | s, a, supply) as empirical frequencies; only pairs with > threshold observations kept
↓ + per-(s,a,s′) reward percentiles
Reward table — 21 percentiles (0th…100th) of shaped reward per transition, one set per (α, γr) config
↓ loaded into
Gymnasium env — reset() samples an initial state + a real calendar window; step() samples s′ ∼ P̂, r ∼ percentiles

The heart of it, from src/environment.py (condensed):

class UserEnv(gym.Env):
    def step(self, action):
        trans_probs = self._get_transition_probabilities(self.current_state, action)
        if trans_probs is not None:
            next_state = tuple(self._sample_next_state(trans_probs))   # s' ~ P̂(·|s,a,supply)
            reward = self._sample_reward(self.current_state, action, next_state)
            self.current_state = next_state + self._get_derived_state_variables(
                self.current_timestep + 1)                             # re-derive supply features
        else:                       # no data for this (s,a) — penalize instead of guessing
            reward = self.unknown_action_reward
        self.current_timestep += 1
        done = self.current_timestep >= self.max_episode_length
        return self.current_state, reward, done, True, {}

    def _sample_reward(self, state, action, next_state):
        row = self.config_df.query(...)         # match (s, a, supply, s'), total > threshold
        percentiles = [f"reward_{i}th_perc" for i in range(0, 101, 5)]
        return np.random.choice(row[percentiles].values[0])   # sample the empirical distribution

    def get_permissible_actions(self, state):
        # actions with enough historical support in THIS state + supply context
        acts = self.config_df.query(...)["action"].unique().tolist()
        return acts if acts else [0]

Three design choices worth defending out loud:

  • Reward percentiles, not means. Storing 21 percentiles per transition and sampling from them preserves the variance of outcomes. Training against means would hand the agent a smoothed world and teach it risk-blindness.
  • Action masking via data support. A state-action pair enters the MDP only with enough historical observations (10K in the sim build). Where the logs are silent, the empirical P̂ and R̂ are garbage — masking stops the agent from exploiting estimation noise. This is offline-RL thinking: stay where the data is.
  • Exogenous supply. Episodes replay real calendar windows, so the agent trains against genuine match-density patterns, not synthetic ones.
The silent assumption that killed it: grouping logs by (s, a) and calling the frequencies P(s′ | s, a) treats correlation as causation. The historical actions weren't randomized — Pacman assigned them based on user attributes, some of which aren't in the 2-D user state. The estimated "effect" of a 100% discount is polluted by who historically got 100% discounts. Hold this thought for the autopsy.

Part 5 — the agents

Tabular Q-learning (what actually shipped)

From src/agents.py — a defaultdict Q-table with visit counts, ε-greedy over the masked action set:

class QLearningAgent:
    def __init__(self, action_space, learning_rate=0.1, discount_factor=0.99,
                 exploration_rate=1.0, exploration_decay=0.995):
        self.q_table = defaultdict(
            lambda: defaultdict(lambda: {"q_value": 0, "visit_count": 0}))

    def get_action(self, state, permissible_actions):
        if random.uniform(0, 1) < self.exploration_rate:
            return random.choice(permissible_actions)          # explore
        return self.get_max_action(state, permissible_actions) # exploit

    def learn(self, state, action, reward, next_state):
        q_predict = self.q_table[state][action]["q_value"]
        max_next_q = max(self.q_table[next_state][a]["q_value"]
                         for a in range(self.action_space))
        q_target = reward + self.discount_factor * max_next_q   # Bellman target
        self.q_table[state][action]["q_value"] += self.learning_rate * (q_target - q_predict)
        self.q_table[state][action]["visit_count"] += 1

Why tabular in production? The effective state space is small — 32 × 6 user states crossed with bounded supply features — and the empirical MDP only defines well-supported cells anyway. A table converges fast at 1M episodes, is trivially serializable (pickle → daily batch scoring), and every decision is inspectable: "why did user X get 50%?" has a lookup-the-cell answer. When the argmax looked weird, you read the Q-values and the visit counts. That debuggability is a feature, not a compromise.

class DQNAgent:
    def _build_model(self):

    def train(self):
        batch = random.sample(self.memory, self.batch_size)     # replay buffer (10K)
        states, actions, rewards, next_states, dones = zip(*batch)
        ...

        next_q    = self.target_net(next_states).max(1)[0].detach()   # frozen target net

Knowing all three levels (from-scratch, SB3, RLlib) is good interview surface: you can discuss what the libraries actually do under the hood because you've written the loop yourself.

The baseline: Pacman

The incumbent policy is a lookup: (churn_bucket, days_inactive) → discount, at a configurable "aggression" level (0.7–0.85 swept). It's exactly the myopic policy the RL agent had to beat — and a strong one, because it was tuned on years of business data.

Part 6 — training at scale

  • 1,000,000 episodes per configuration, ε decaying 1.0 → 0.01 across training.
  • Sweeps as a Cartesian product: 4 learning rates × selected (α, γr) reward shapes × 4 Pacman aggression levels for the baseline arm — 40+ configs per sweep, so 40M+ simulated episodes per run.
  • Distributed by config: a controller script fanned each config out as a separate Databricks job via the Jobs API — embarrassingly parallel, no Ray cluster needed for the tabular agent.
  • Everything logged: per-episode reward, retention, spend, policy overlap with Pacman, unknown-action rate, exploration rate → Delta tables (summary + per-timestep raw), with the agent pickle and full config JSON alongside. Model selection = best terminal reward per reward shape, then a 100K-episode re-evaluation of the winners.

This is the part of the story that reads "ML infra maturity": hyperparameter sweeps as cattle, full experiment lineage, reproducible selection. Same muscle as a post-training sweep over KL coefficients and LRs.

Read that table honestly and the story is: the agent bought its retention. Higher raw retention, but strictly worse efficiency across every hyperparameter setting. The reward shape under-priced spending (α too generous, γr too flat in the shipped config), and the agent did exactly what it was paid to do — which was not quite what the business wanted. Part 9 — autopsy: why sim gains didn't transfer

1. The simulator was not causal. The transition estimates P̂(s′ | s, a) came from logged data where Pacman chose the actions. Users who historically received aggressive discounts were systematically different (in ways the 2-D user state can't see) from users who didn't. So the model's implied effect of switching someone's action is biased — classic confounding. In the sim, the agent exploited response patterns that were artifacts of the old targeting rule, not causal effects available for the taking. Online, those gains evaporated. The retro line: "the response estimates were not causal and were confounded by factors not incorporated in the MDP state."

2. The state was too coarse for the Markov property to hold. Two dimensions of user state (recency × churn quintile) means everything else that drives promo response — tenure, spend level, favorite format, price sensitivity — lives outside the state and acts as an unmodeled confounder. The Markov assumption wasn't approximately true; it was doing load-bearing work it couldn't support.

3. The reward was mis-specified. Independent of causality, the shipped shape under-penalized spend and the agent overspent by 50% in sim. Two of the three failure modes were visible before going live — the sim's own efficiency table said so.

The one-line verdict, which is also the best thing you can say in an interview: "we learned that constructing a reliable simulator is a harder problem than the RL itself." The team's subsequent direction — and the textbook one — is offline RL that never trusts a simulator: learn directly from logged transitions while constraining the learned policy to stay near the data-generating policy, and evaluate with off-policy estimators (importance sampling) before anything goes live.

The RLHF bridge (use this). "Constrain the learned policy near the behavior policy that generated your data" is the same principle as the KL penalty to the reference model in RLHF/GRPO — same failure mode being prevented, too: a policy exploiting regions where its value estimate (or reward model) is extrapolating without data support. Reward hacking, distribution shift, staying on-support — this project and post-training are the same ideas wearing different clothes.

How I'd do it today (the forward-looking answer): (1) estimate promo uplift causally first — randomized logging or doubly-robust estimators — and build rewards on uplift, not raw response; (2) skip the simulator, go straight to offline RL on logged transitions with pessimism/behavior constraints; (3) gate deployment on off-policy evaluation, not simulator returns; (4) richer state via user embeddings (this is exactly the itch LUMOS later scratched — one foundation model's representations replacing hand-picked state features).

Part 10 — grill Q&A: the questions an RL person will actually ask

Why tabular Q-learning in production and not your DQN?

The masked, data-supported state space is small — 32 × 6 user states crossed with bounded supply context, minus all cells without 10K observations. A table converges fast, has zero training instability, serializes to a pickle for daily batch scoring, and every decision is a readable cell with a visit count next to it. The DQN existed and matched it in sim; it added the deadly-triad risk surface and removed inspectability, for no measurable gain at this state-space size. Staff answer: model capacity should match problem capacity, and the bottleneck here was never the function approximator — it was the fidelity of the MDP.

Why γ = 1? Isn't that dangerous?

Divergence risk from γ = 1 is an infinite-horizon problem — returns are bounded by the fixed 10-step episode. And the business objective is literally "sum of DAU over the window," with no preference for early days, so any γ < 1 would distort the objective, telling the agent day-2 retention matters more than day-9. Finite horizon plus timestep-in-state is the principled way to do undiscounted control.

Q-learning is off-policy. Where did that actually matter here?

Twice. In sim training, the behavior policy is ε-greedy (mostly random early on) while the target is the greedy max — that's what lets 1M noisy episodes converge toward Q*. And it matters conceptually for the pivot: off-policy methods are the only family that can learn from logged data generated by Pacman, which is what the offline-RL direction requires. On-policy methods (SARSA, vanilla policy gradient) can't touch that data.

How did you handle state-action pairs with no data?

Three mechanisms. In the MDP build: pairs below the observation threshold simply don't exist in the transition table. In the env: stepping into an unknown pair returns a penalty reward (a variant env instead freezes the timestep). At inference: get_permissible_actions() masks the argmax to supported actions only, with no-promo as the fallback. It's a crude form of the pessimism principle — never let the policy express confidence where the data is silent. The principled version of this instinct is exactly what behavior-constrained offline RL formalizes.

Why did simulation results not transfer online?

Because the simulator's dynamics were estimated from observational data. P̂(s′|s,a) conflates "what a discount causes" with "who used to get discounts" — the old targeting policy is a confounder living outside the 2-D user state. The agent optimized against biased counterfactuals; online, the bias didn't pay out. Secondary: the reward under-penalized spend, which the sim's own retention-per-rupee table flagged before launch. Lesson stated plainly: sim-to-real for user behavior is a causal-inference problem, and building the simulator is harder than the RL.

Why not just a contextual bandit / uplift model?

The honest answer: for the 10-day horizon we could support, a well-built uplift model might have matched us — and it's the right first rung. The case for RL is the sequential structure: discounts change tomorrow's state, budget couples decisions across days, and supply features ("save the big discount for the IPL match") only pay off with lookahead. The principled framing is that bandits are the special case (horizon 1) and we wanted the general machinery in place for longer horizons — but I'd concede the crawl-walk-run critique and start with uplift today.

How was the budget constraint actually enforced?

Not with constrained-MDP machinery in v1 — honestly. Three practical layers: the reward shape prices spend into every decision (soft constraint); the action set caps per-user promo value; and experiment-level budget was set by cohort sizing. Lagrangian CMDP and an LP allocation layer over Q-values were designed but not shipped in my phase. Knowing the gap and the fix is the defensible position.

Maximization bias — did your Q-values overestimate?

Structurally yes — the max over sampled empirical rewards guarantees some upward bias, and we didn't ship Double Q-learning. Two mitigants: action masking kept the max over a small supported set (bias grows with the number of noisy options), and 1M episodes over a small table shrinks per-cell variance a lot. The visible symptom of residual optimism was the agent's spend aggression. Right fix if it had mattered more: Double Q-learning — two tables, select with one, evaluate with the other.

How did you evaluate the policy before going live?

Simulator returns plus policy-overlap-with-Pacman as a sanity metric — and that was the gap. There was no off-policy evaluation on held-out logged data before v1; the simulator was the (flawed) evaluator. Today I'd gate on importance-sampling OPE: weight logged returns by π(a|s)/β(a|s), check effective sample size, and refuse to ship if the estimate or its variance is bad. That gate would have caught this policy before burning an experiment window on it.

What does this have to do with RLHF?

Nearly everything transfers. Reward mis-specification → reward hacking (my agent bought retention the way a chat model buys thumbs-ups with sycophancy). Staying near the behavior policy in offline RL → the KL-to-reference penalty in PPO/GRPO. OOD action masking → pessimism about states the reward model hasn't seen. Even the operational shape rhymes: sweep reward/constraint hyperparameters, evaluate offline, then pay for a small online test. I did the whole loop on users before I did it on language models.
