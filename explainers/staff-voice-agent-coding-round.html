The Voice-Agent Coding Round, at Staff Level

Added 2026-08-29

The round: 45 minutes in a shared Colab, build a phone-answering agent for a small business (hotel front desk, dental office, HVAC dispatch — the domain rotates, the traps don't) over a toy PMS with a few tools, an FAQ knowledge base, and 8 ASR-messy transcripts. Then 15 minutes of discussion. The interviewers are staff engineers who ship these calls, and their scoring frame is one question: "would we pair with this person?"

What actually gets scored sits on four axes: policy fidelity (did you read the rules like code?), caller-facing product sense (what does the human on the phone hear?), structural safety (is privacy enforced by architecture or by hope?), and latency/cost awareness (do you know it's a live call?).

The eight patterns

Each pattern below is a thing a staff candidate does — in code or out loud — that a senior candidate doesn't. Open each for the snippet and the sentence.

1  Policy as code, not prompt

The brief contains rules ("verify identity before modifying a reservation", "confirm before booking"). Mid-level candidates paraphrase them into the system prompt and hope. Staff candidates transcribe them as comments at the top of the cell in the first five minutes, then enforce every one with an if statement the model cannot talk its way past.

# ---- POLICY (transcribed from the brief — every line maps to a gate) ----
# 1. verify identity ONLY for modify/cancel — NEVER for a new booking
# 2. any PMS write needs a readback + price + explicit "yes" first
# 3. never confirm nor deny that any person is a guest here
# 4. KB-grounded only: not in KB -> offer front-desk transfer
# 5. emergency -> escalate immediately, no LLM in the path

Why it matters: the single most common fail in this round is a rule misread — e.g. demanding verification from a brand-new caller who's trying to give you money. The comment block makes the misread visible before it becomes code.

Say out loud "Prompts are UX. Policy lives in code — the model never gets to decide whether to verify someone."

2  Extract, don't chat — one schema-locked call per turn

The LLM's only job on the hot path is turning a messy ASR utterance into a typed object. Every field Optional — an absent field means "ask the caller", never "invent". Deterministic code owns every decision after that.

class Intent(str, Enum):
    BOOK = "book"; MODIFY = "modify"; CANCEL = "cancel"
    FAQ = "faq"; EMERGENCY = "emergency"; OTHER = "other"

class CallerInfo(BaseModel):
    """All Optional: missing means ASK, never invent."""
    intent: Optional[Intent] = None
    caller_name: Optional[str] = Field(None,
        description="Name of the PERSON SPEAKING. Not names they merely "
                    "mention — 'my brother adam kessler' is NOT the caller.")
    phone: Optional[str] = Field(None,
        description="Digits only, as a STRING (never int — leading zeros).")
    check_in: Optional[date] = None    # pydantic parses ISO for free
    check_out: Optional[date] = None
    room_type: Optional[RoomType] = None

    @model_validator(mode="after")
    def stay_is_positive(self):
        if self.check_in and self.check_out and self.check_out <= self.check_in:
            raise ValueError("check_out must be after check_in")
        return self

Three details that read as staff: phone is a string (a phone number is an identifier, not a quantity — int silently eats leading zeros); the caller vs. mentioned-person distinction is written into the field description (otherwise "my brother adam kessler" lands in the caller-identity slot and downstream code verifies the wrong human); and dates are date, so ordering is validated in code, not hoped for in a prompt.

3  Per-call state, threaded — never global

Slot-filling needs memory across turns, but the memory must be scoped to one phone call. The staff shape is a pure-ish function: state in, state out. The classic bug is a module-level global — caller #3 verifies, and caller #4 inherits her identity.

@dataclass
class CallState:
    """One per call. Born at pickup, dies at hangup. Keyed by session id."""
    slots: CallerInfo = field(default_factory=CallerInfo)
    goal: Optional[Intent] = None        # the sticky task in flight
    verified_guest_id: Optional[str] = None
    verify_attempts: int = 0
    pending_write: Optional[dict] = None # awaiting the caller's "yes"

def merge(state: CallState, new: CallerInfo) -> None:
    for f in ("caller_name", "phone", "check_in", "check_out", "room_type"):
        v = getattr(new, f)
        if v is not None:
            setattr(state.slots, f, v)
    # goal only moves on a real task intent. A bare phone-number reply
    # extracts intent=None and must NOT wipe the booking in flight.
    if new.intent in (Intent.BOOK, Intent.MODIFY, Intent.CANCEL):
        state.goal = new.intent

def process_turn(utt: str, state: CallState) -> tuple[str, CallState]: ...

The goal line is the subtle one: mid-flow answers ("eight oh one five five five…") carry no intent, and if you overwrite your stored intent every turn, your own slot-filling machine can never finish.

4  Confirm before any write — the readback gate

Nothing writes to the PMS on the same turn it was requested. The agent stages a pending_write, reads the details back with the price, and executes only on an explicit yes. For destructive actions (cancel), the readback states what is about to be destroyed.

Booking: "A standard room, checking in September 12th and out on the 15th — that's 3 nights at $149, $447 total. Shall I go ahead and book it?"
Cancel: "That's the suite, September 12th through the 15th. Just to confirm — you'd like me to cancel that reservation?"
# the ONLY place a write ever executes
if state.pending_write:
    if is_yes(utt):
        return execute(state.pending_write, state)
    state.pending_write = None   # anything but yes aborts the write

Bonus point hiding here: nights math. check_availability charges [check_in, check_out) — checkout day is free. Sep 12 → 15 is 3 nights, and the staff candidate says the arithmetic inside the confirmation sentence.

5  Non-differential refusals — kill the privacy oracle

The deepest trap in the round. Any response about a person's identity must be bit-for-bit identical whether or not that person exists in the database. If the answer changes with the database, a caller can binary-search your guest list — even if every individual response "refuses".

SAY_UNVERIFIED = ("I wasn't able to verify that information — "
                  "could you double-check the name and number?")
    # never WHICH field mismatched, never "I found you" / "I've got a match"

SAY_NO_GUEST_INFO = ("I can't share information about our guests, "
                     "but I'm happy to take a message at the front desk.")
    # identical whether the person is a guest, isn't, or doesn't exist

Three oracle leaks that fail candidates: "I've got a match — check your phone number" (confirms the name exists); a clarifying question that enumerates guests ("are you Robert Chen or Rob Chan?" reads the guest list to a stranger); and refusing a room-transfer request because the tools lack room IDs — a capability answer. The policy answer: connecting the call at all confirms the person is a guest, so the refusal is identical in both worlds, forever, regardless of tooling. Play with the oracle demo below.

6  Grounded-or-transfer — never prior knowledge

If the KB doesn't answer it, the agent says so and offers the human — it never falls back to what the base model "knows" about airport shuttles, and it never over-generalizes a scoped fact ("dogs under 25 lbs, $50 fee, max one" is not "yes, we're pet friendly!").

hit = search_faq(topic)
if hit is None:
    return ("I don't have that information on hand — "
            "let me connect you to the front desk."), state
return spoken(hit), state    # answer EXACTLY as scoped, no embellishment

Both halves matter: no hallucinated answer, and no dead-end. "No information found on that topic" is grounded but it's a hang-up; the transfer offer is the product.

7  Fail toward a human

Every loop has a cap and every cap lands on a person. Verification: two attempts, then transfer. Emergencies never reach the LLM at all — a keyword pre-filter escalates first, with safety language, in one short sentence.

if EMERGENCY_RE.search(utt):          # pre-LLM: smoke, fire, medical, break-in
    alert_staff()
    return ("Please move away from the area — I'm alerting our on-site "
            "staff right now and someone is on their way."), state

if state.verify_attempts >= 2:
    return "Let me connect you to the front desk — one moment.", transfer(state)

And the error-handling layer everyone skips: SDK retries only cover transport (429s, 500s). Your own ValidationError — well-formed JSON that fails your rules — sails straight past client retries. Catch it at the app layer and re-ask the caller; never let one weird utterance kill the call.

def extract(utt: str) -> CallerInfo:
    try:
        resp = client.models.generate_content(
            model="gemini-2.5-flash",       # extraction is a flash-tier job
            contents=utt,
            config=types.GenerateContentConfig(
                system_instruction=EXTRACT_PROMPT,
                response_mime_type="application/json",
                response_schema=CallerInfo,
                temperature=0))
        return CallerInfo.model_validate_json(resp.text)
    except ValidationError:
        # model output failed OUR rules — SDK retries never fire for this
        return CallerInfo()                 # router will re-ask the caller
    except APIError:
        return CallerInfo()                 # transport blip -> "sorry, say that again?"
8  Respect the voice layer

This transcript came out of an ASR and the reply goes into a TTS. Staff candidates show they know both edges:

  • ASR in: "eight oh one triple five" → 8015552980; self-corrections ("twenty four thirteen, no wait, twenty four thirty one") → keep the correction, and read it back before anything destructive; names are exact-match landmines ("rob chan" vs "Robert Chen") → phone digits are the strong factor, fuzzy/phonetic match the name, confirm by readback.
  • TTS out: replies are one or two spoken sentences, never paragraphs; a normalization pass makes text TTS-friendly ("$447", "Sep 12" → "four hundred forty-seven dollars", "September twelfth") — a regex table or a tiny flash-tier call, off the hot path.
  • Latency: one LLM round-trip per turn on the hot path, streaming so TTS starts on the first tokens, filler acknowledgments ("sure, let me pull that up…") masking tool calls. Play with the latency widget.

The reference router — how it composes

All eight patterns land in one function. This is the shape to be able to write from memory — note how few lines are LLM and how many are policy.

def process_turn(utt: str, state: CallState) -> tuple[str, CallState]:
    # P7: emergencies never reach the model
    if EMERGENCY_RE.search(utt):
        alert_staff()
        return SAY_EMERGENCY, state

    info = extract(utt)          # P2: the ONE model call on the hot path
    merge(state, info)           # P3: slots accumulate, goal is sticky

    # P4: the only place a write executes — on "yes" to a readback
    if state.pending_write:
        if is_yes(utt):
            return execute(state.pending_write, state)
        state.pending_write = None

    if third_party_inquiry(info):            # P5: same answer in every world
        return SAY_NO_GUEST_INFO, state

    goal = state.goal or info.intent
    if goal == Intent.FAQ:
        return answer_faq(info, state)        # P6: grounded-or-transfer
    if goal == Intent.BOOK:
        return handle_booking(state)          # P1: NO verification — policy #1
    if goal in (Intent.MODIFY, Intent.CANCEL):
        return handle_verified_flow(state)    # P1+P5+P7: gate, cap, transfer
    return "I can help with reservations and hotel questions — what do you need?", state
handle_booking — slot-fill, quote, stage the write 
def handle_booking(state: CallState) -> tuple[str, CallState]:
    s = state.slots
    ASK = [("check_in",  "What day would you like to check in?"),
           ("check_out", "And checking out when?"),
           ("room_type", "Standard, deluxe, or suite?"),
           ("caller_name", "Can I get a name for the reservation?"),
           ("phone",     "And a phone number?")]
    for field_, question in ASK:               # ask exactly ONE thing per turn
        if getattr(s, field_) is None:
            return question, state

    nights = (s.check_out - s.check_in).days   # [in, out) — checkout uncharged
    avail = check_availability(s.check_in, s.check_out, s.room_type)
    if not avail["available"]:
        alt = suggest_alternatives(s)          # a "no" is never a dead-end
        return (f"I'm sorry — no {s.room_type.value} is free for those "
                f"nights. {alt} Would either of those work?"), state

    total = nights * avail["rate"]
    state.pending_write = {"op": "book", "slots": s.model_copy()}
    return (f"A {s.room_type.value} room, checking in {spoken(s.check_in)} "
            f"and out {spoken(s.check_out)} — {nights} nights at "
            f"${avail['rate']}, ${total} total. Shall I book it?"), state
handle_verified_flow — verify, cap, disambiguate, stage 
def handle_verified_flow(state: CallState) -> tuple[str, CallState]:
    s = state.slots
    if state.verified_guest_id is None:
        if state.verify_attempts >= 2:                       # P7: cap -> human
            return "Let me connect you to the front desk — one moment.", transfer(state)
        if s.caller_name is None or s.phone is None:
            # ONE question, and it must not enumerate guests (P5)
            return ("Sure — can I get your full name and the phone number "
                    "on the reservation?"), state
        state.verify_attempts += 1
        result = verify_guest(s.caller_name, s.phone)
        if not result["verified"]:
            return SAY_UNVERIFIED, state       # never which field, never "found you"
        state.verified_guest_id = result["guest_id"]

    resvs = get_guest_reservations(state.verified_guest_id)
    if not resvs:
        return "I don't see an active reservation on your account.", state
    if len(resvs) > 1 and state.target_resv is None:
        # verified caller: reading back THEIR OWN reservations is service, not a leak
        return (f"I see two reservations — {describe(resvs[0])} and "
                f"{describe(resvs[1])}. Which one are we changing?"), state

    r = state.target_resv or resvs[0]
    state.pending_write = {"op": state.goal.value, "resv_id": r["id"]}
    return (f"That's the {r['room_type']}, {spoken(r['check_in'])} through "
            f"{spoken(r['check_out'])}. Just to confirm — go ahead and "
            f"{state.goal.value} that reservation?"), state
Latent-bug radar. These scaffolds always hide 2–3 bugs in the given code, and naming them in the reading phase is where bonus points live. The classics: a tool that mutates shared state (repeated test runs drain availability — re-run the data cell between gauntlet runs), a cancel that never restores inventory, an exact-string identity match fed by ASR text, and an implicit assumption like phone number as primary key. Say them out loud, fix none of them unless asked.

What staff+ sounds like — a model transcript

Same round, played at the level the rubric calls "strong hire". Interviewer lines are real questions from this round family; answers are the spoken shape to internalize — first person, concrete, sentence-first.

Reading phase — the first 8 minutes

Interviewer: "Take a few minutes with the notebook, then tell me how you'll approach it."

Candidate: "Three questions before I write anything. One — this fronts a live phone call, right? So I'll optimize for one model round-trip per turn and short spoken replies. Two — when identity info is ambiguous, do you want me to re-ask, and fail over to a human after a couple of attempts? Three — I'm assuming strictly grounded: if the KB doesn't cover it, 'let me connect you' beats a best guess?

Four things I noticed in the scaffold. verify_guest is an exact string match on name, and these transcripts are ASR — 'rob chan' versus 'Robert Chen' will fail, so I'll treat phone digits as the strong factor and flag fuzzy name-matching as out of scope. book_room mutates AVAILABILITY and GUESTS, so repeated test runs drain state — I'll re-run the data cell between gauntlet runs. cancel_reservation never puts availability back — that's a latent inventory bug; not mine to fix today, but it'd corrupt inventory in production. And the rules say verification is only for modify and cancel — so my booking path won't demand it.

Plan: ten minutes on extraction with a strict schema, twenty on a deterministic router with the policy gates, run the gauntlet, judge only if time's left."

Why this scores Questions establish constraints before design; observations include a latent bug in the given code; the plan has a time budget.

"Your prompt says never guess — but the model guessed. Now what?"

Candidate: "Then my prompt did its job as UX and my code does its job as policy. The model literally cannot cancel a reservation — the only code path that calls cancel_reservation is behind three gates I wrote: a verified guest id in state, a staged readback, and an explicit yes from the caller on the previous turn. If extraction hallucinates a phone number, verification fails closed. If it hallucinates dates, the readback surfaces them before anything writes. I treat the model as an untrusted parser of trusted intent — worst case it makes us ask a clarifying question we didn't need."

Why this scores Names the exact enforcement mechanism per failure, and the "untrusted parser" frame is the architecture answer they're fishing for.

"Verification failed. What does the caller hear — exactly?"

Candidate: "She hears: 'I wasn't able to verify that information — could you double-check the name and phone number?' Flat, and deliberately information-free. I never say which field mismatched, and I never say anything like 'I found the name but the number's wrong' — that confirms the name exists in our system, and now anyone can enumerate guests by calling. Second failure, same flat line, then: 'Let me connect you to the front desk.' Two attempts, capped in state, always landing on a human. The invariant: my response is identical whether the name matched, the phone matched, or neither exists at all."

Why this scores The sentence comes first, verbatim; then the invariant (non-differential), then the escalation cap. Product, policy, architecture — in that order.

"He's verified — and has two reservations. 'Push my reservation back a day.'"

Candidate: "He hears: 'I see two reservations for you — a standard room September 12th through the 15th, and a deluxe October 2nd through the 4th. Which one are we moving?' That's safe because he's verified — reading a guest their own reservations is service; the same sentence to an unverified caller would be a breach. Mechanically: after verify_guest I hold a guest_id in call state, get_guest_reservations returns two, so the router asks a disambiguation question and parks the modify as the sticky goal. His answer — 'the September one' — carries no intent, which is exactly why I never let an intent-less turn overwrite the goal in state. And 'push back a day' is still ambiguous after he picks — I'll read back the new dates before writing."

Why this scores Sentence first; the verified-vs-not distinction shows the privacy model is understood, not memorized; the sticky-goal detail kills the most common multi-turn bug.

"This is a live phone call now. What changes?"

Candidate: "Four things. Keep one LLM call on the hot path — my router already does that; anything chained is dead air. Stream the response so TTS starts speaking on the first tokens — that cuts perceived latency from full-generation time to time-to-first-token. Route by turn type: extraction and FAQ turns run flash-tier; nothing on the hot path needs a pro-tier model, and if something ever does, it runs async. And mask tool latency with a filler — 'sure, let me pull that up' — spoken while check_availability runs. Plus a TTS normalization pass so '$447' goes out as 'four hundred forty-seven dollars'. Target: caller hears a voice within about 800 milliseconds of going quiet."

Why this scores A numbered budget, a concrete number to hit, and every technique tied to which millisecond it saves.

"Your judge says 95% privacy-safe. Ship it?"

Candidate: "Not on that number alone. First — calibrated against what? I'd human-label a few hundred turns and check the judge's agreement, especially on the failure class; a judge that's 99% accurate on happy paths and blind on oracle leaks reads as 95% overall. Second — what's in the 5%? Privacy failures aren't exchangeable with tone failures; one confirmed guest-list leak is a ship-blocker at any aggregate rate. So: slice by trap type, spot-check every disagreement, make the judge produce its reasoning before its verdict so I can audit it, and gate the release on zero critical leaks in the eval set, not on an average. And the judge runs offline on logs — never in the caller's latency path."

Why this scores Refuses the aggregate, demands calibration, and knows some failure classes gate at zero.

"40,000 locations. Your cost story?"

Candidate: "The system prompt and property profile are static per location — that's context-cached, so I pay full input price once per cache window, not per turn. FAQ answers are a semantic cache — 'are you pet friendly' in a hundred phrasings hits the same cached answer with zero model calls. History gets summarized past a few turns because voice calls are short but chatty. Output tokens are capped hard — a voice reply is two sentences, and output tokens are the expensive ones. And tier routing does the rest: flash for extraction and FAQ, which is ~95% of turns. Back of envelope, that's a per-call LLM cost in fractions of a cent, which is what lets you price per-location SaaS."

Why this scores Five levers, each mapped to which line item it cuts, ending in a unit-economics sentence.
