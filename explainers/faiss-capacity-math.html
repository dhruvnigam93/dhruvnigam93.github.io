The One Formula You Keep Forgetting

›

Every capacity question in an interview reduces to one of three computations. Memorize the template, plug in numbers live.

Memory (how big is it?) N items × D dimensions × bytes_per_element = raw bytes
Latency (how long to scan?) bytes_to_scan ÷ memory_bandwidth = seconds
QPS (how many requests?) DAU × sessions/day × fetches/session ÷ 86,400 × peak_factor = peak RPS
These three are the atomic building blocks. Every "how would you scale this" question is just these composed together. The interview error is knowing the concepts but not being able to produce the number live.

FAISS Index Types — What Actually Happens Per Query

›

The interview error: name-dropping "FAISS" while describing brute-force cost. Here's what each index actually computes.

Flat (Brute)
IVF
PQ
IVF+PQ

IndexFlatL2 / IndexFlatIP

What it does: Computes exact distance from query to every single vector. No approximation.

Per-query cost N × D multiplications + N × D additions = O(N × D)
1B × 128 = 128 billion ops = DON'T USE THIS AT SCALE
Memory N × D × 4 bytes (FP32)
1B × 128 × 4 = 512 GB

When to use: Baselines, small datasets (<1M), re-scoring top-K from another index, or on GPU where bandwidth compensates (A100 scans ~500M vectors/sec for D=128).

This is what you quoted in the interview: "n × d computations." Correct for Flat. Wrong claim if you said FAISS — FAISS's value IS the non-brute-force indexes below.

IndexIVFFlat

What it does: K-means clusters the dataset into nlist cells. At query time, finds the closest nprobe centroids, then brute-force scans only vectors in those cells.

Step 1: Find closest centroids nlist × D = cheap (nlist is ~10K-100K, D is 128)
e.g., 32K × 128 = 4M ops — microseconds
Step 2: Scan vectors in probed cells (N / nlist) × nprobe × D = vectors_scanned × D
Rule: nlist ≈ √N → each cell has √N vectors
1B vectors, nlist=32K → ~31K vectors/cell
nprobe=32 → scan 32 × 31K = ~1M vectors
1M × 128 × 4 bytes = 512 MB → ~10ms at 50 GB/s
Memory = same as Flat (vectors stored as-is) 512 GB + centroid overhead (negligible)
The rule: nlist ≈ √N. For 1B vectors → nlist ≈ 32K. For 100M → nlist ≈ 10K.
nprobe controls the recall/latency trade-off. nprobe=1 is fast but low recall. nprobe=√nlist is a reasonable default.

IndexPQ (Product Quantization)

What it does: Splits each D-dim vector into m sub-vectors of D/m dimensions. Each sub-vector is quantized to the nearest centroid from a learned codebook of 256 entries. The full vector becomes m bytes.

Compression ratio Original: D × 4 bytes (FP32) → Compressed: m bytes
D=128, m=32 → 512 bytes → 32 bytes = 16× compression
D=128, m=16 → 512 bytes → 16 bytes = 32× compression
D=128, m=8 → 512 bytes → 8 bytes = 64× compression
Memory for 1B vectors Raw: 512 GB
PQ m=32: 1B × 32 = 32 GB
PQ m=16: 1B × 16 = 16 GB ← fits one machine
PQ m=8: 1B × 8 = 8 GB ← fits GPU VRAM
Distance computation Pre-compute distance table: D × 256 ops (once per query)
Per-vector: m lookups + m additions → O(m) not O(D)
Speedup: D/m × (since lookup replaces multiply)

Recall cost: m=32 → ~95%+ recall@100. m=8 → ~80-85%. OPQ (rotation before PQ) adds ~2-5% recall for free.

IndexIVFPQ — The Production Index

What it does: IVF clustering + PQ compression. The workhorse for billion-scale. This is what you should default to in interviews.

Per-query cost 1. Centroid search: nlist × D (microseconds)
2. Scan probed cells: (N/nlist) × nprobe vectors
3. Each vector is PQ-compressed → m table lookups, not D mults

1B, nlist=32K, nprobe=64, m=32:
Scan: 64 × 31K = 2M vectors × 32 bytes = 64 MB → ~1.3ms
Memory 1B × m bytes + centroid overhead
m=32: ~32 GB — single machine, RAM
m=16: ~16 GB — fits in GPU VRAM
Interview default: "For 1B vectors at 128 dimensions, I'd use IVF32K,PQ32. That's ~32GB, fits one machine, queries in ~1-3ms at nprobe=64 with ~95% recall@100. If I need to cut memory further, PQ16 halves it to 16GB at ~90% recall."

The template that works for any system.

The template peak_RPS = DAU × sessions_per_day × requests_per_session ÷ 86,400 × peak_factor

Ranker Capacity Math — The Missing Piece

›

The ranker is the expensive part — it runs a neural net on every candidate.

Ranker Cost Per Request

The math Per request: score K candidates through a model
Model inference: ~0.1-1ms per candidate (CPU) or ~0.01-0.1ms (GPU, batched)

Example: 100 candidates, CPU ranker 100 × 0.5ms = 50ms per request At 200K RPS → need 200K × 0.05s = 10,000 CPU cores

Example: 100 candidates, GPU ranker (batched) Batch all 100 → one forward pass ~1-3ms At 200K RPS → 200K × 0.002s = 400 GPU-equivalents

Sharding — When and How to Split the Index

›

Here's the full decision framework.

Why Shard?

  • Memory: Index doesn't fit on one machine (IVFFlat at 1B×128d = 512GB)
  • QPS: Single machine can't handle the request rate
  • Latency: Scanning a huge index on one machine exceeds SLA

Two Strategies

Data-parallel (shards)
Replicas

Split the data across machines. Each shard holds N/S vectors. Query hits ALL shards in parallel, each returns top-K, merge at the aggregator.

Per-shard scan (IVFPQ, 1B vectors, 10 shards) 100M per shard, nlist ≈ √100M ≈ 10K
nprobe=64: 64 × 10K = 640K vectors × 32B = 20MB
Latency: 20MB ÷ 50GB/s ≈ 0.4ms

But: scatter-gather overhead 10 RPCs (fan-out) + merge = ~2-5ms network overhead
Total: ~3-6ms per query

When: Index doesn't fit on one machine, or per-machine scan exceeds SLA.

More shards = more fan-out RPCs = higher tail latency. Don't shard for fun. If IVFPQ32 fits in 32GB on one box, replicate, don't shard.

Full copy of the index on multiple machines. Load balancer distributes queries. Each machine handles 1/R of the QPS.

Replicas for QPS Single machine throughput: ~1000-5000 QPS (IVFPQ, multi-threaded)

200K peak RPS ÷ 3000 QPS/machine = ~67 replicas
Each replica = 32 GB (IVFPQ32) → total RAM: ~2.1 TB

When: Index fits on one machine but QPS requires horizontal scale.

Interview line: "The index is 32GB with IVFPQ, so it fits on one machine. My bottleneck isn't memory — it's QPS. I need ~67 replicas at 3K QPS each to handle 200K peak RPS. That's 67 × r6i.4xlarge at ~$1/hr = ~$49K/month for the retrieval tier."

Interview Cheat Sheet — Say These Lines

›

Scripted lines for when you're asked about capacity. Practice saying them out loud, modifying the numbers for the specific problem.

Opening (first 5 minutes — ASK, don't assert)

"Before I design anything — what scale are we talking about? DAU, item corpus size, latency SLA, and is there a cost envelope I should respect?"

When asked "how does this scale?"

"Let me work through the numbers. [DAU] × [sessions] × [fetches] ÷ 86,400 × [peak factor] gives me [X]K peak RPS. That's the load my retrieval and ranking tiers need to handle."

When asked about the index

"At [N] vectors and [D] dimensions, raw FP32 is [N×D×4] bytes. I'd use IVFPQ with [m] sub-quantizers — that compresses to [N×m] bytes, which [fits/doesn't fit] on one machine. Query latency: nlist ≈ √N ≈ [X]K, at nprobe=[Y] I'm scanning [Y × N/nlist] vectors × [m] bytes = [Z] MB. At 50 GB/s memory bandwidth, that's about [Z/50000]ms."

When asked about cost

"Retrieval tier: [R] replicas at ~$1/hr = $[R×730]/month. Ranker: [G] GPU instances at ~$1/hr = $[G×730]/month. The ranker dominates — it's where I'd optimize first: smaller model, distillation, or reducing candidates from 100 to 50 if recall allows."

When asked "what breaks at 10×?"

"10× DAU means 10× RPS. Retrieval: 10× replicas, which is cost but not architecture change. Ranker: 10× GPU fleet — that's where I'd push back and ask if we can reduce candidates or use a cheaper model for most traffic. The index itself doesn't change; it's the serving fleet that scales linearly with QPS."
