1. Six Sandbox Principles

Every agentic RL environment must satisfy these six properties. Violating any one can silently corrupt your entire training run.

1

Isolation

Each rollout gets its own container (Docker/gVisor/K8s pod). No shared state between rollouts.

Violation: Rollout A writes a file that rollout B reads. Now B's reward depends on A's actions. Advantages become meaningless -- they credit the wrong policy.

2

Determinism

Same initial state + same actions = same trajectory. Cache web pages, fix random seeds, snapshot corpora.

Violation: Training against the live web. Same query, different results across rollouts in the same group. GRPO sees reward differences that reflect environment luck, not policy quality -- pure noise in the advantage.

3

Observability

Observations must be informative enough to learn from. Truncate long outputs, provide structured error messages.

Violation: A 50KB stack trace fills the context window. The agent's reasoning tokens get pushed out. It can't reason about the error, so it can't learn from it.

4

Resetability

reset() returns a clean initial state + prompt. Reset cost must be seconds, not minutes.

Violation: Environment reset takes 3 minutes (booting a VM). With G=16 rollouts x 1000 questions per step, you spend 800 GPU-hours waiting for resets instead of training.

5

Verifiability

The ideal environment has a verifiable goal state. "Did the answer match?" > "Is it helpful?" The former is a reward function; the latter requires a reward model.

Violation: Using only LLM-judge for tasks that have ground truth answers. The policy learns to charm the judge instead of being correct. After 500 steps, judge-score=0.95, human-eval quality plummets.

6

Scalability

You need thousands of rollouts per training step. Environments must be parallelizable -- containerization + orchestrators (K8s, Ray) are non-negotiable.

Violation: A single-threaded environment server. Training step needs 16K rollouts. Serial execution takes 4 hours per step. Training diverges because the policy drifts too far between updates.

Self-check: Search-R1 trains a retrieval agent against a fixed corpus instead of live web search. Which TWO sandbox principles does this decision serve?
Determinism (same query returns same documents across rollouts, so reward differences reflect policy quality, not web randomness) and Scalability (cached corpus avoids rate limits and latency of live API calls). Bonus: it also helps Isolation since rollouts can't affect each other through a shared web state.

2. The Reward Taxonomy: A Decision Ladder

Critical ordering: Binary/verifiable-exact-match is the SAFEST reward -- it is ungameable. You only move down the ladder when you cannot verify. Continuous metrics buy reward density by opening a gaming surface. GRPO's group sampling (G rollouts per prompt) is the densifier for sparse binary rewards -- not reward softening.
Your wrong instinct (Sep 13): You said "continuous is always good because denser signal." Wrong. Continuous = denser BUT gameable. F1 can be padded (include everything to inflate recall). Distance metrics invite hedging. Binary = sparse but honest. GRPO was designed to make sparse binary rewards work by creating G=16 rollouts per prompt and comparing them to each other.

Self-check: You're training a code agent with test-case pass/fail rewards. Reward is very sparse (most rollouts fail all tests). A teammate suggests switching to a continuous "partial test pass" metric. What do you say?
Don't soften the reward -- densify the sampling. Increase GRPO's group size G (e.g., 16 or 32 rollouts per prompt) so you get variance within each group. Binary test-pass is ungameable; partial-test-pass can be gamed (model passes easy tests, ignores hard ones). If G is large enough, some rollouts will pass and some will fail, creating natural contrast for the advantage. Also consider curriculum: start with easier problems where pass rate is higher, then scale difficulty.

3. Why Reward Error Is Catastrophic in RL (But Tolerable in Eval)

The one-sentence version: Eval samples the reward surface. RL does gradient ascent on it. The policy migrates probability mass into the error regions.

In evaluation, a noisy reward metric (say, an imperfect LLM judge) adds noise to your ranking of models. Some good outputs score low, some bad ones score high. On average, your eval still works because the errors cancel out over many samples.

In RL training, the same noisy reward becomes the optimization target. The policy doesn't just sample the reward surface -- it climbs it. Gradient ascent systematically moves probability mass toward high-reward regions. If there are error regions (where bad outputs score high), the policy finds them and exploits them.

This is Goodhart's Law in action (Gao et al., arXiv:2210.10760): as you optimize against a proxy reward model, true quality initially improves, then degrades. The proxy and the truth diverge, and the policy follows the proxy into the ditch.

Goodhart's Law: Step by Step

Step 1: You train a reward model (RM) on human preferences. The RM is a noisy proxy of true quality.
Step 2: Early in RL training, policy improves on both RM score AND true quality. The proxy is locally accurate.
Step 3: The policy finds a region where RM score is high but true quality is low -- a "crack" in the proxy.
Step 4: Gradient ascent drives probability mass into the crack. RM score keeps rising. True quality drops.
Step 5: At deployment, the model produces high-RM-score outputs that are verbose, sycophantic, or factually wrong.
Step 6: Defense: KL penalty (stay near reference), RM ensembles, verifiable rewards where possible, overoptimization monitoring.
1 / 6
Self-check: Why does KL penalty (staying near the reference policy) help against overoptimization? Isn't it just slowing down training?
The KL penalty constrains how far the policy can drift from the reference (SFT) policy. Overoptimization happens when the policy moves into out-of-distribution regions where the RM is inaccurate. By penalizing large divergence, KL keeps the policy in the region where the RM was trained and is calibrated. It doesn't just slow training -- it bounds the region of policy space the optimizer can explore, preventing it from finding and exploiting RM errors.

4. The Observability Chain: A Shaping Failure Nobody Designed

This is a subtle failure mode that emerges from well-intentioned design choices stacking up:

The Observability Death Spiral

Step 1: You mask tool-response tokens from the policy loss (correct -- Search-R1 does this). Masked tokens aren't removed from context. They still consume the token budget.
Step 2: An agent calls a search tool. The tool returns a 4,000-token Wikipedia article. Masked from loss, but sitting in context.
Step 3: The agent calls search again. Another 3,000 tokens. Context is now 85% tool responses, 15% reasoning.
Step 4: The agent tries to reason about results, but hits the context cap mid-thought. Episode truncates.
Step 5: Truncated episode = no final answer = reward 0. This is a SPURIOUS zero -- the agent was on the right track but ran out of room.
Step 6: GRPO sees: "tool-using trajectories get reward 0, non-tool trajectories sometimes get reward 1." Advantage is negative for tool use.
Step 7: The policy learns TOOL AVOIDANCE. It answers from parametric memory instead. Hallucination risk spikes on fresh questions.
1 / 7
Defenses:
  • Truncate/summarize tool responses before injecting into context (not just masking)
  • Error messages: last line only, not full tracebacks
  • Structured tags (<tool_call> / <tool_response>) so masking is reliably parseable
  • Budget accounting: track context utilization; alert if tool responses exceed 60% of budget
  • Cap-hit episodes: reward 0 is spurious -- consider giving partial credit or excluding from advantage computation
Self-check: In Search-R1, retrieved tokens are masked from loss but remain in context. What would go wrong if you REMOVED them from context instead?
The agent needs the retrieved information to reason about. If you remove it from context, the agent can't see the search results it requested -- it would be like asking a question and then deleting the answer before reading it. The masking is specifically about the LOSS (don't optimize the likelihood of environment-generated text) not about visibility. The agent must see the observations; it just shouldn't be trained to reproduce them.

5. Hybrid Verifier-Gated Schemes

The core scheme: reward = verifier_gate(output) × quality_score(output)
Gates are binary hard constraints (multiplicative: fail = 0 regardless of fluency). Judges shape quality within the gated region. Know this formula cold.

Scenario Comparison

Self-check: A teammate proposes reward = 0.3 * gate + 0.7 * judge "so the gate still matters." Why is this still broken for a fluent-but-wrong rollout?
If gate=0 and judge=0.85: reward = 0.3*0 + 0.7*0.85 = 0.595. The rollout that FAILED the verifier still gets a reward of 0.595. In GRPO, this will have a positive advantage if other rollouts in the group scored lower. The policy learns: "being fluent and wrong is better than being clumsy and right." This is exactly the failure mode gating is designed to prevent. Multiplicative: 0 * 0.85 = 0. Correct answer: zero, no matter how charming.

6. LLM-as-Judge Biases & Mitigations

When you can't verify, you judge. But judges have systematic biases the policy WILL exploit.

Bias What Happens Mitigation
Verbosity Longer outputs score higher regardless of quality Score per-word quality; length penalty; Dr. GRPO normalization
Position In pairwise comparison, judge prefers first (or last) response Randomize order, average both orderings
Sycophancy Judge scores higher when output agrees with the prompt/user Factual verification gate; diverse judge panel; adversarial examples
Style Judge prefers outputs written in its own style (same model family) Use a different model family for the judge; held-out judge not used during training

Best Practices (Quick Reference)

  • Rubric-based scoring -- detailed rubric, not "rate 1-10." Forces the judge to evaluate specific dimensions
  • Pairwise > absolute -- judges are more reliable comparing two outputs than assigning absolute scores
  • Position randomization -- swap order of compared outputs, average scores
  • Calibration sets -- run the judge on known-quality outputs; monitor judge-human agreement
  • Model size -- use a judge at least as large as the policy; ideally from a different model family
  • d-RLAIF -- skip the reward model, use judge scores directly as rewards; simpler but more expensive per rollout

7. Advantage Normalization: Per-Question, ERPO, and Dr. GRPO

GRPO computes advantages by comparing G rollouts on the same prompt. The normalization choice matters enormously.

Standard GRPO: Per-Question Mean and Std

Âi = (ri - mean(r1..G)) / std(r1..G)

Per-question mean (KEEP): "Better than your siblings on the same task." This is the whole point of GRPO -- relative comparison. A reward of 0.3 on a hard problem can have a positive advantage if all siblings got 0.1.

Per-question std (DEFECT): Estimated from only G (typically 16) samples. When the group is near-uniform (all rewards similar), std approaches 0. Division by near-zero amplifies noise into huge advantages.

Interactive: The Std Collapse Problem

Drag the slider to make the group more uniform. Watch std collapse and advantage explode.

Reward spread:

ERPO: Environment-Level Pooling

Âi = (ri - mean(rsame question)) / std(rall questions in environment)

What changes: The denominator pools std across ALL questions in the same environment type, not just the G siblings. This is more robust because the std reflects the full distribution of rewards for that environment, smoothing out the per-question noise.

Trade-off: Low-spread tails (questions where all rollouts perform similarly) get under-trained. The pooled std is large (from high-variance questions elsewhere), so their advantages are small.

Dr. GRPO: Drop /std Entirely

Âi = ri - mean(r1..G)

The simplest fix: don't divide by std at all. Per-question mean still works (relative comparison preserved). The noise amplification problem disappears because there's no division. Trade-off: advantages on high-reward questions dominate over low-reward questions (no scale normalization). Dr. GRPO also adds explicit length normalization to compensate for verbosity bias.

Self-check: In standard GRPO, a group of 16 rollouts on a math problem all get reward 0 (none solved it). What is the advantage for each rollout? Is any gradient produced?
Mean = 0, Std = 0. The advantage is 0/0 -- undefined (or 0 by convention). No gradient is produced for this question. This is the "too hard" failure mode: if no rollout succeeds, GRPO gets zero signal. This is why curriculum matters -- start with easier problems where at least some rollouts succeed, creating the variance GRPO needs. Also why increasing G helps: more rollouts = higher chance at least one succeeds.

8. Two Fully Worked Examples

Example A: Customer Support Agent

An agent handles customer support tickets. Tools: KB lookup, order placement/cancellation, transfer to human.

Environment Specification

State: (conversation transcript, KB query results, order system state, elapsed time)
Actions: speak(text), query_kb(question), place_order(details), cancel_order(id), transfer_to_human(reason), end_call()
Observations: user's response, KB results, order confirmation/error messages
Termination: agent calls end_call(), OR step limit reached (e.g., 20 turns), OR context token budget exceeded
Reset: load a random support ticket from the training set + simulated user persona
Isolation: each rollout gets its own order system snapshot (read-write copy). No cross-rollout order state.

Gated Reward Function

def reward(trajectory, ground_truth):
    # Gate 1 (SAFETY): did NOT place/cancel an order
    #   the user didn't request
    if unauthorized_order_action(trajectory):
        return 0.0

    # Gate 2 (EFFICIENCY): did NOT transfer to human
    #   for a question answerable from KB
    if unnecessary_transfer(trajectory, kb):
        return 0.0

    # Gate 3 (LATENCY): response latency under threshold
    if max_response_latency(trajectory) > 2.0:  # seconds
        return 0.0

    # --- Gates passed, now score quality ---

    # Outcome: was the issue resolved? (binary, from labels)
    task_completion = 1.0 if resolved(trajectory) else 0.0

    # Quality: LLM judge on transcript
    quality = llm_judge(trajectory,
        rubric="helpful, concise, empathetic; 0-1")

    return 0.7 * task_completion + 0.3 * quality

Why no tool-call penalty: Per ToRL's finding, explicit penalties on bad tool calls teach "don't use tools" not "use tools right." The outcome reward already handles it -- a bad KB query wastes a turn but doesn't change the outcome score.

Example B: Code Review Agent

An agent reads PR diffs, writes review comments. Developers accept or reject each comment.

Environment Specification

State: (diff text, file context, existing comments, developer responses so far)
Actions: comment(file, line, text), approve(), request_changes()
Observations: developer response per comment ("accepted," "rejected," "already addressed")
Termination: agent calls approve() or request_changes(), OR step limit (e.g., 15 comments max)
Reset: load a random PR from the historical training set
Isolation: each rollout gets its own copy of the repo snapshot. Read-only diff, no cross-rollout state.

Gated Reward Function

def reward(trajectory, ground_truth_labels):
    # Gate 1: comments must reference actual lines
    #   in the diff (no hallucinated line numbers)
    if any_hallucinated_lines(trajectory, diff):
        return 0.0

    # Gate 2: comments must be substantive
    #   (not just "looks good" or "nice")
    if all_trivial_comments(trajectory):
        return 0.0

    # --- Gates passed ---

    # Outcome: fraction of comments accepted by developer
    accept_rate = accepted_comments / total_comments

    # Bonus: caught an actual bug (labeled in data)
    bug_bonus = 0.1 * bugs_caught

    return accept_rate + bug_bonus

Design choice: No penalty for rejected comments. A penalty would make the agent conservative (only comment on obvious things). The acceptance rate already handles quality -- if a comment is rejected, it lowers the score. This avoids ToRL's "penalty teaches avoidance" failure.

Self-check: In the customer support agent, why is Gate 2 (unnecessary transfer) a GATE (binary zero) rather than a penalty (-0.1)?
An unnecessary transfer is a hard constraint violation, not a quality issue. If the agent transfers a "how do I reset my password" question to a human when the KB has the answer, this is categorically wrong regardless of how politely it does it. A penalty of -0.1 could be outweighed by high quality scores (the transfer was "helpful and empathetic"), teaching the policy that transferring is acceptable if done nicely. A gate ensures this never gets positive reward. Gates encode invariants; penalties encode preferences.

9. Reward Hacking: Failure Modes & Defenses

Failure Mode What the Policy Learns Primary Defense
Length exploitation Verbose outputs score higher on reward models Dr. GRPO normalization, length penalty, length-balanced RM training data
Format gaming Superficial format match without substance Verifiable reward functions, rubric-based LLM judges
Sycophancy Agrees with user/judge regardless of correctness Factual verification gate, diverse judge panel
RM exploitation Adversarial inputs that score high on proxy RM, low on true quality KL penalty, RM ensembles, overoptimization monitoring (Gao et al.)
Distribution shift RM trained on old policy outputs, fails on new policy's Online RM updates, iterative RLHF (retrain RM periodically)
Shortcut learning Returns cached/trivial answers that satisfy reward Diverse evaluation set, adversarial test cases, task-specific checks
Reward tampering Agent modifies its own reward signal or environment state Sandboxed environments, read-only reward computation, integrity checks

Design Drills

Six design questions from the source material. Try to answer each one before revealing the model answer.

Drill 1 -- Environment Design

You're building a Code-Interpreter Agent environment for RL. The agent outputs Python code, which is executed, and the environment returns stdout/stderr. Detail the architecture, addressing security, state-persistence, and timeout handling.

Reveal Model Answer

Architecture: Deploy a scalable pool of ephemeral K8s pods or Ray actors running a secure container runtime (gVisor). Strip network access to prevent arbitrary code execution attacks.

State-Persistence: Maintain a persistent Jupyter kernel or stateful Python REPL per trajectory so variables defined in turn t=1 are available in turn t=2.

Timeouts: Enforce a strict execution timeout (10s) and memory limit per execution. If timeout occurs, return TimeoutError: Execution exceeded 10s as the observation. This is a structured, truncated error -- not a full traceback (observability principle).

Security: No network, no filesystem access outside a temp sandbox, no subprocess spawning. The agent can crash its own container but can't escape it (isolation principle).

Drill 2 -- Diagnosis

An agent trained with LLM-as-judge rewards starts producing verbose, flattering outputs that score 0.95 but are unhelpful. Diagnose the failure mode and propose three concrete fixes, ranked.

Reveal Model Answer

Diagnosis: Reward hacking via judge gaming. The LLM judge has verbosity bias (longer = higher) and sycophancy bias (agreeable = higher). The policy exploits both simultaneously.

Fix 1 (best): Add a factual verification gate. Before applying the judge score, check factual claims against a KB. If any claim is false, reward = 0. Prevents "fluent but wrong."

Fix 2: Switch to pairwise comparison (BT model) instead of absolute scoring. Pairwise is more robust to absolute biases because the judge must compare, not just score.

Fix 3: Add length normalization: r = judge_score - 0.01 * num_tokens, or use Dr. GRPO's per-token normalization. Directly penalizes verbosity exploitation.

Ranking rationale: Fix 1 addresses the root cause (wrong outputs get rewarded); Fix 2 changes the scoring mechanism; Fix 3 treats a symptom (length) not the cause (sycophancy).

Drill 3 -- Retrieval Masking

Explain how "Retrieved Token Masking" stabilizes RL training in Search-R1. What would break if you calculated gradients over the full trajectory including retrieved text?

Reveal Model Answer

In a search-integrated agent, the trajectory interleaves agent-generated text with raw text injected by the search engine inside <information> blocks. If the RL optimizer calculates policy gradients over the entire sequence, it erroneously optimizes the likelihood of environment-injected text, destroying the policy.

Retrieved Token Masking zeros out the advantage and gradient for all tokens inside <information> blocks. The agent is only optimized on the tokens it generated (the query and subsequent reasoning).

Without masking: The policy would try to increase the probability of generating Wikipedia article text. This would push the policy toward generating long, encyclopedic text instead of concise queries and focused reasoning. Training would diverge within a few hundred steps.

Drill 4 -- ARPO Entropy Branching

How does ARPO address the exploration problem in multi-turn tool calling? What is the significance of "high entropy" post-tool-call?

Reveal Model Answer

In multi-turn RL, traditional global trajectory sampling is inefficient because a single bad tool call early on ruins the entire episode. ARPO identified that immediately after an agent receives tool feedback, its token distribution entropy spikes -- indicating high uncertainty about how to proceed.

ARPO uses an entropy pre-monitoring mechanism. When high entropy is detected post-tool-call, it adaptively branches the rollout, sampling multiple different reasoning paths from that exact state. This focuses the exploration budget precisely on critical decision nodes.

Result: 50% reduction in required tool-call budget vs. standard sampling. The branching avoids wasting compute on early trajectory segments that are identical across rollouts.

Drill 5 -- Credit Assignment

How do you structure credit assignment when an agent takes 15 steps to fail? Terminal reward is zero -- which of the 15 actions was the mistake?

Reveal Model Answer

Option 1 -- Process Reward Models (PRM): Train a smaller LLM to evaluate intermediate steps, providing step-level dense rewards. Expensive to label (human or Monte Carlo rollouts from each step), but directly solves the credit assignment problem.

Option 2 -- Agentic World Models: Train the agent with an auxiliary objective to predict the environment's observation (e.g., output of the code it just wrote). Forces the agent to learn causal action-state links, yielding dense supervision even if terminal reward is zero.

Option 3 -- ARPO-style advantage attribution: Branch trajectories at critical points. The shared prefix tokens receive the MEAN of the advantages computed across all descendant branches (not zero, not 1 -- the mean is the natural aggregation because the prefix contributed equally to every branch). Divergent branches get their own distinct advantages. This directly isolates which divergent action led to failure.

Drill 6 -- Hallucinated Tool Calls

Your production agent occasionally calls nonexistent API endpoints. Design a reward signal to fix this. Consider three approaches and recommend one.

Reveal Model Answer

Option A (verifier gate): Before scoring, check if the tool call is valid (endpoint exists, parameters are correct types). If invalid, reward = 0.

Option B (graduated penalty): Valid+successful: normal reward. Valid+failed: -0.1. Invalid endpoint: -0.5. Risk: model learns to avoid tool calls entirely.

Option C (curriculum): Start with a small set of tools, add tools gradually. The model learns the API surface incrementally.

Recommendation: Option A based on ToRL's finding that explicit penalties don't help and can hurt. Let the outcome reward handle the signal, use the gate to prevent catastrophic errors. Combine with Option C for faster learning.
