0 · The 30-second opener

Lead with honest I-vs-we and land the scope. This is the frame everything else hangs on.

"I built the real-time voice agent for Dream11's live cricket streams — a speech-to-speech companion users talk to while watching a match. Speech-to-speech is Gemini Live; my work was the agent layer around it: the LiveKit transport, the retrieval and tool-calling that grounds it in live match state and player chatter, the latency engineering to hold felt-latency under ~2s across an India-to-US hop, and the eval harness. It ran through IPL 2026 — ~1M users exposed, ~1.5M conversation-minutes, concurrency capped at 10K by Gemini's session quota."

Why it works: names the model as someone else's, claims the systems work as yours, states scale once. Never imply you trained the S2S model.

1 · Architecture & region placement

Walk me through the topology

"Draw the path from the user's mouth to the answer."

Two hops, deliberately asymmetric:

  • User device → agent server: WebRTC (UDP) over LiveKit. User in India, agent in us-east-1.
  • Agent server → Gemini Live: a stateful WebSocket (TCP), agent co-located with the model, both in us-east-1.

The design decision (your strongest moment — lead with it): the agent lives next to the model, not next to the user. The client→agent leg is WebRTC/UDP — loss-tolerant, no head-of-line blocking, it survives a long transcontinental hop. The agent→Gemini leg is WebSocket/TCP — retransmits + HOL blocking make a cross-region hop deadly. So you put the fragile TCP leg inside one region and let the resilient UDP leg absorb the distance.

This predated LiveKit publishing the same best practice. Say that.

3 · Turn detection & endpointing

What makes the end-of-turn decision — and is it "semantic"?

"You called it 'semantic' twice and couldn't name the model correctly either time."

First, decide who even owns endpointing — this is the real architecture question and you must pin it before an interview:

  • Option A — Gemini Live's native VAD/turn-taking. A realtime S2S model does its own server-side endpointing. If you relied on this, say so plainly: "Gemini Live handled turn-taking natively; we tuned its sensitivity."
  • Option B — your own VAD + turn detector before committing audio. Silero VAD for speech/no-speech, then a turn detector for end-of-utterance probability, then commit to Gemini.

If Option B, the precise, correct statement (see the reference card): at IPL 2026 LiveKit's turn detector was the transcript-based MultilingualModel — a Qwen2.5-0.5B-Instruct running on the STT stream (~50–160ms/turn, CPU). LiveKit's audio-native detector (v1/v1-mini) shipped ~June 2026 — after IPL. So don't call your IPL system audio-native.

The line to say: "VAD gives speech/no-speech. On top, a turn detector predicts end-of-utterance probability so we don't barge in on a mid-sentence pause — that's the 'semantic' part, using context not just silence energy. At IPL that was the transcript-based model; the audio-native one came later. Honest gap: I never measured a field false-start rate — I tuned the silence window (~300ms) by manual testing, ~15–20 trials per setting across devices. If I redid it: log dual-channel audio, compute a real false-start / cut-off rate, and A/B the audio-native detector."

The trap: "semantic endpointing using Silero" (Silero is a plain acoustic VAD — nothing semantic) and "fine-tuned Qwen, audio-native" (the Qwen model is the transcript one). Both are precision cracks of the same shape as calling DeBERTa-v3 "BERT v3."

5 · Retrieval — the three paths

How does the agent know things about the match?

Three distinct information paths, chosen by the model via tool calls:

  1. Live match state — a Redis key (match_id → current-state JSON: score, wickets, over, highlights). ~50ms. Fast, structured, always current.
  2. Player/team chatter — a sub-agent (Gemini Flash) that queries a document DB of Reddit/Twitter chatter (~150–200 tracked entities, refreshed every 6h). This is the "what's everyone saying" path.
  3. Open facts — the same sub-agent does grounded Google search over a curated allowlist of reliable stat/news domains.

Naming the three cleanly is the frame. The gaps live in which path serves a given question (§9) and whether the retrieved fact survives into the spoken answer (§10).

6 · Retrieval — BM25 in Postgres

What actually computes the BM25 score?

"You said 'BM25 on a Postgres table.' Native Postgres FTS is not BM25."

The correct, non-fatal phrasing (full detail in the reference card):

"We used the pg_search (ParadeDB) extension — it embeds Tantivy into Postgres for true BM25, so we got IDF, TF saturation (k1), and length normalization (b). Native ts_rank gives none of those — it only has local term frequency and blunt length bitmasks, so it's vulnerable to keyword stuffing. And I'll be honest about scale: after the entity + 7-day filter we're often down to ~20 candidate docs, so BM25 is doing little today — it's future-proofing. At today's size, an exact match sorted by recency would be almost as good."

The trap: "I think your Postgres version already supports BM25" — it doesn't, and that sentence proves you don't know how either algorithm works. Also don't oversell a 10K-doc corpus that filters to 20; own that the metadata filter is doing the retrieval, not BM25.

7 · Retrieval — the query & expansion

In an audio pipeline, where does the query text come from?

"BM25 is lexical — its quality is 100% the query string. Who writes it?"

  1. Gemini Live emits text alongside audio. It produces both modalities and can return the user-input transcript too — no added latency. So you do have the running transcript. (This corrects the earlier "no transcript" claim.)
  2. On a tool call, the primary model emits a short query line ("Bumrah economy this season").
  3. The Flash sub-agent gets the full conversation context + that line, does entity recognition + query expansion, and builds the structured filter (entities, 7-day window) plus the expanded lexical query that hits BM25.
The trap: speculative expansion that "anticipates what else is interesting" pads the query with terms the user didn't say — great for recall, corrosive for BM25 precision. You're covered only because your ablation (§8) showed expansion net-helped. Say "expansion, bounded by the ablation," not "expansion, because more context is better."

8 · Retrieval — eval & the vector ablation

How do you know it retrieves the right thing?

"Not the end-to-end LLM judge — the retrieval layer specifically."

This was your strongest thread of either session. It's the template for how every answer should sound:

  • Built a synthetic known-item set (~250 conversations), each with a target doc ID the query should surface.
  • recall@10 ≈ 80% (confirm; and confirm whether that's BM25-alone or the hybrid — state the delta).
  • Tried dense / hybrid retrieval — it did not beat BM25 + expansion.
  • Failure mechanism (this is the money sentence): dense retrieval pulled semantically adjacent, wrong-entity docs — Kohli-retirement chatter scoring high on a Rohit query — which crowded out the correct doc in the top-10. On a jargon-heavy, well-summarized corpus, lexical matching + interpretability won.

Keep the interpretability argument: with BM25 you can reason about why a doc ranked; dense similarity is opaque. That's a legitimate staff-level reason to not add complexity.

10 · Faithfulness vs factual accuracy

How do you know the spoken answer used what you retrieved?

"...vs the model ignoring your tool result and hallucinating from memory?"

Mechanism (good — keep it): the tool returns structured JSON (facts + trend summary + a few example posts); the tool definition carries persona-specific few-shot examples of how to fold a result into speech. And the honest caveat: "there's no hard guarantee it uses the tool over its parametric memory — you iterate the tool definition + system prompt until you observe it does."

The distinction you missed — say it explicitly: your post-session judge measures factual correctness (extract claims → verify via search), which is not the same as faithfulness to retrieval (did the spoken answer actually reflect the retrieved context). Two consequences to own:

  • A correct-but-ungrounded answer (model got lucky from memory) passes your check.
  • Gossip claims are unverifiable by a search judge — so the exact corpus you built (chatter) has no faithfulness check at all.

Honest close: "A true faithfulness metric — compare the spoken claim against the retrieved passage — is a gap I'd fix with an entailment/grounding judge over the retrieved context."

11 · Async tool-calls & hiding latency

How do tool calls not blow the latency budget?

Async, non-blocking, with verbal filler: when the model wants a tool, it emits a filler utterance ("let me check the TV") and the function call together. The agent runs the tool while the filler plays; the result feeds a second inference.

  • Tool latencies (verify): Redis live-state ~50ms; the RAG sub-agent ~1s (two Flash calls ≈ 800ms + DB ~100ms + provider-side grounding).
  • ~10% of turns hit a tool.
  • The honest reframe: "sub-2s" = time-to-filler, not time-to-answer. Time-to-answer = TTFB + tool + second inference.
The trap: quoting the RAG path at "500–600ms." Two Flash inferences alone are ~800ms; with the DB and grounding it's ~1s. State ~1s first — don't get walked there by arithmetic. The ~1–1.5s filler barely covers a 1s RAG path, so precision here matters for the UX story.

12 · War stories (personal bugs)

The single hardest bug you personally debugged

"Not a design decision — a bug. Symptom → trace → fix. Your hands."

This was your biggest exposure — three asks, zero bugs, last time. You now have two. Rehearse both cold:

Story 1 — the silent retrieval failure

Symptom: retrieval returned nothing for the first days post-deploy, but nothing was flagged. Trace: the Postgres doc DB wasn't reachable from the LiveKit-hosted agent; tool calls failed non-blocking and Google results papered over it, so transcripts looked fine. Caught it manually — inserted test docs, saw they were never retrieved. Root cause + insight: graceful degradation masked a hard failure. Fix: added tool-failure observability + an eval that checks whether turns that should have triggered a tool actually did.

Story 2 — the tool result that interrupted the user

Symptom: async tool results, when they landed, cut the user off mid-sentence — abrupt and rude. Fix: gate delivery on LiveKit's speaking-state — if the user is talking, hold the result and fold it into the agent's next turn; only speak immediately on silence.

Still missing: a genuinely code-level bug (a race, an ordering/concurrency bug, a data-structure bug) in your own code. Story 1 is ops, Story 2 is interaction logic. Find one more from the async/query path and rehearse it — that's the remaining staff-level hole.

13 · The spoiler / sync problem

Your feed is ahead of the user's stream — spoilers?

Honest framing (unmeasured, unsolved, mitigated): the vendor data feed lags ~1–2s; the broadcast the user watches lags ~10–60s. So the agent literally knows the future — a wicket the user hasn't seen. Mitigation: reactive-only design — proactivity disabled, so the agent never volunteers an event ahead of the user. The real fix (say this, it shows you understand it): sync agent world-state to the user's playback position via a client playhead heartbeat, and gate any event by the user's stream timestamp.

The trap: "I think by then they're still in sync" — that's a hand-wave. The delta was never measured. Own that: "unmeasured, mitigated by reactive-only; here's how I'd measure and fix it."

14 · The eval framework

How did you evaluate the whole thing?

Your other strong answer — use this register everywhere: post-hoc over transcripts, offline + a daily online watch.

  • Tool-call correctness — a Gemini-Flash judge scores should-have-called vs did-call.
  • Repetition index — a 4/5-gram repeat metric that drove system-prompt fixes for catchphrase spam.
  • Factual verification — claims extracted and checked via search (with the faithfulness caveat in §10).
  • Policy/abuse checks.
  • True turn latency — offline dual-channel VAD analysis to measure real end-of-turn timing (still excludes client network legs — know this caveat).
  • Traces in Langfuse.

★ Reference: BM25 in Postgres verified 2026

Native Postgres FTS is NOT BM25. tsvector / ts_rank / ts_rank_cd lack all three BM25 pillars:

  • No IDF — no corpus-wide term rarity; scores only on the current doc's term counts.
  • No TF saturation (k1) — repeat-term value doesn't flatten, so keyword stuffing wins.
  • Crude length norm (no b) — blunt integer bitmasks instead of average-doc-length normalization.

True BM25 inside Postgres — the real extensions:

ExtensionWhat it is
pg_search (ParadeDB)The production answer. Embeds Tantivy (Rust Lucene) via pgrx. Full BM25 + faceting, Elasticsearch-like.
vchord_bm25 (VectorChord / TensorChord)Ultra-light, Block-Max WAND, native custom index. Optimized for speed & low footprint.
ZomboDBLegacy. Real BM25 but by shadow-syncing to an external Elasticsearch/OpenSearch cluster — you're running a JVM search cluster underneath.

Sober take for a ~20-doc filtered candidate set: BM25 is mathematical theater — IDF earns its keep when ranking the top-10 out of 100k+ matches, not 20. An exact match + recency sort is honest at that scale.

★ Reference: LiveKit turn detector verified 2026

LiveKit ships two different turn detectors. Conflating them is the crack.

Text (MultilingualModel)Audio (v1 / v1-mini)
InputSTT transcript + contextRaw audio waveform, no transcript
BaseQwen2.5-0.5B-Instruct, 0.5B, 396MB, CPU, ~50–160ms/turnArchitecture undisclosed
StatusDeprecated (removal in SDK 2.0)Current default, shipped ~June 2026
Multilingual~13 langs (incl. Hindi)14 langs, per-lang thresholds

Both sit on top of a VAD (e.g. Silero). VAD = speech/no-speech energy + silence timeout. The turn detector adds an end-of-utterance probability from context/prosody, so mid-sentence pauses don't trigger a barge-in.

The self-contradiction to never repeat: "fine-tuned Qwen, audio-native" — the Qwen model is the transcript model; the audio-native one's base is undisclosed. And it shipped after IPL 2026, so your IPL system was the transcript model (or Gemini Live's native turn-taking). Audio-native peers for reference: Pipecat/Daily "Smart Turn" (v2 = Wav2Vec2 ~95M; v3 = Whisper-Tiny encoder ~8M).

★ Delivery rules (the meta-patterns)

  1. State a number once, correctly. Both sessions, numbers drifted upward under arithmetic (latency 600ms→1s; docs 10K→20). Pre-compute the latency budget and the numbers triangle so you never revise mid-sentence.
  2. Flag uncertainty out loud. You state guesses ("your PG version supports BM25", "fine-tuned Qwen") with the same confidence as facts. Say "I'd have to check the base model" — an interviewer can't tell your knowledge from your invention otherwise.
  3. Volunteer your own gaps. Coverage holes and unmeasured metrics read as senior when you name them, weak when the interviewer digs them out.
  4. Lead with mechanism, not outcome. Your best moments (region placement, the dense-crowds-top-10 ablation) were mechanism-first. Make every answer sound like those.
  5. Kill the tics. No "right?" tail; don't garble the stack names (Silero, Langfuse) — rehearse saying them aloud.
