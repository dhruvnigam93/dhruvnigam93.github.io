Added 2026-08-19

Plug in your real production numbers. Every panel recomputes live and tells you whether the story triangulates — because an interviewer will do this math while you talk. Latency is pre-filled with the calibrated first-principles breakdown (p50/p90 presets); scale and cost carry the Aug 19 grill answers.

1 · Latency budget — the components must sum to what you measured

Latency = user stops speaking → user hears first audio. Client in India; LiveKit SFU, agent, and Gemini all in us-east-1. The allocation method: pin what's physics — India↔us-east one-way is ~100–120ms (RTT ~200–240ms over SEA-ME-WE + transatlantic routes), speed-of-light-bound and low-variance, so uplink + downlink + jitter ≈ 0.39s at p90. Pin what's config — endpointing is deliberately ~0.33s. The model TTFT is the free variable — everything you can't pin is Gemini: 2000 − 390 − 330 ≈ 1250ms, exactly right for flash-class S2S under real ingress jitter. Then validate, don't assume: read RealtimeModelMetrics.ttft (activityEnd sent → first audio byte). If it reads ~0.8s instead, the missing ~450ms is an inflated client jitter buffer on a poor Indian ISP — a network fix, not a model fix.

2 · Scale — calls, minutes, and concurrency must describe the same season

Three claims live together: total watchtime (1.5M min), peak concurrency (10K), and the implied usage behind them. They're coupled: calls/day × avg call length × days must land on total minutes, and daily minutes spread over the active window gives your average concurrency — which the peak claim gets judged against. In the grill, "40–50K calls/day" and "hit 10K on 20 days" both collapsed against the 1.5M total. Find the set that's actually true.

3 · Cost — what a session-minute burns, and what the season cost

Two linear meters run during every session: LiveKit bills per connection-minute, and Gemini bills per audio token — input tokens accrue for the whole session (the mic streams continuously), output tokens only while the agent speaks. Know your cost per minute cold: "what did this cost?" is a favorite staff-level question, and it also explains why you gated at the quota instead of buying provisioned throughput.

4 · The answers — say it like this

The spoken versions that survive follow-ups, distilled from the Aug 19 grill. Rule that fell out of the session: the hedges predicted the cracks — every number said with "I think" later collapsed, every number said plainly held. State it once, correctly, or say "I'd want to check." Never revise a number mid-sentence.

"Walk me through the system."
Phone connects over WebRTC; the LiveKit SFU, our agent server, and Gemini all sit in us-east-1; the agent holds a WebSocket to Gemini's native speech-to-speech model (16kHz PCM in, 24kHz out). At the agent: background-voice cancellation and endpointing — Silero VAD silence gating plus a turn-detector model, ~300ms combined. On end-of-turn, audio goes to Gemini; response audio streams back the same path. Tools run at the agent — async, never blocking.
"Gemini does the speech-to-speech. So what's actually yours?"
Everything except the model weights: the agent framework and serving path, the two-hop WebRTC/WebSocket architecture, endpointing, and the context system — a live match feed aggregated into Redis behind a score tool, a curated search index of credible cricket sources, and a gossip knowledge base scraped from Twitter with real-time retrieval. Plus memory management and the entire eval framework. Before S2S models matured we ran an LLM+TTS cascade — SSML control, Roman/Devanagari script handling, pronunciation dictionaries — so we also know exactly what the S2S model replaced.
"Break down your sub-2s latency."
Define it first: user stops speaking → user hears first audio; client in India, everything else in us-east-1. Pin what's physics — India↔us-east one-way is ~100–120ms — so uplink + SFU jitter ~160ms and downlink + client jitter + decode ~230ms at p90. Pin what's config: endpointing ~330ms (Silero VAD + turn detector). In-region hops ~40ms. The residual is the model: Gemini Live TTFT ~1.25s p90 (~600ms p50). Total ≈ 2.0s p90, ~1.2s p50. And we validated the residual against RealtimeModelMetrics.ttft rather than assuming — if TTFT had read ~0.8s, the missing ~450ms would have been client jitter buffers on poor ISPs: a network fix, completely different from a model-thinking-level fix.
"Why is the agent in Virginia when your users are in Mumbai?"
We deployed in India first and latency got worse by 2–4 seconds. The client→agent leg is WebRTC over UDP — loss-tolerant, no head-of-line blocking — it survives a long hop. The agent→model leg is a WebSocket over TCP — retransmits and head-of-line blocking make cross-region deadly. So you co-locate the agent with the model, not the user. We worked this out months before LiveKit published it as best practice.
"Don't tool calls blow the budget?"
All tool calls are async by design decision — a blocking tool call means two model inferences and a guaranteed budget breach. Gemini emits a natural filler ("let me check the TV") plus the function call simultaneously; the agent runs the tool — Redis <50ms, search ~100ms, RAG ~50ms — and returns the result for a second inference. About 10% of turns hit a tool. Honest caveat, said before they ask: sub-2s is time-to-first-audio; time-to-the-actual-answer on a tool turn is longer.
"How does end-of-turn detection work?"
Silero VAD silence gating plus a turn-detector model — ~300ms combined endpointing budget (p50 300 / p90 330), set in config as the false-start/latency trade-off: silence gating decides when to cut, the turn detector vetoes cuts mid-thought. We never instrumented false-start rate in production — that's a real gap. Know this config cold: the grill broke it in both directions (first "semantic," then "just 200ms of silence"). One config number, said once, plainly.
"Your data feed is ahead of the broadcast. Does the agent spoil the match?"
Feed lag was 1–2s for tier-one matches; broadcast lag 10+ seconds — so yes, the agent knows the future and we never fully solved that. We contained it by making the agent strictly reactive — proactivity was deliberately disabled — and we saw no spoiler complaints or eval failures. The real fix is syncing agent world-state to the player position via a playhead heartbeat from the client; that's what I'd build next.
"Give me the usage numbers."
Exposed to ~1M users of 5–6M IPL DAU behind a gate; ~15K calls/day average (peak days 40–50K); average call 1–2 minutes with a 7–10 minute tail; ≈1.5M conversation-minutes over ~65 days. Concurrency was capped at 10K — the per-account Gemini Live session quota — and we brushed that cap a handful of times; the exposure gate existed precisely to stay under it without buying provisioned throughput in our first season. Say "capped at," never "scaled to" — the second phrasing invites the arithmetic that breaks it.
"How did you eval a voice agent?"
Transcribe everything, then: a Gemini-Flash LLM judge scoring should-have-tool-called vs did (tool-call accuracy tracked continuously); a 4/5-gram repetition index per conversation — it caught the persona spamming catchphrases and drove system-prompt fixes; policy checks (betting, player abuse); factual-claim verification via search. Latency: dual-channel session audio + offline VAD to mark true end-of-turns. Traces in Langfuse.
"Tell me about a bug you personally debugged in it." OPEN GAP — asked 3×, answered 0×
This needs two or three rehearsed stories before the next real interview, each in the shape: symptom → trace → root cause → fix → what it taught you about the system. Mine the git log, incident threads, and memory for candidates (endpointing misfires, WebSocket reconnect storms, tool-call schema mismatches, audio format bugs). Architecture stories don't count — the interviewer is testing whether you lived in this code.
