RL on LLMs is a Systems Problem

Added 2026-09-03

Most explanations of RLHF and GRPO stop at the math: policy gradient, clip ratio, KL term. Then you try to actually run it and discover the math was the easy part. Online RL on a language model is not a training job — it's a training job, an inference service, and a scoring pipeline welded together, fighting over the same GPU memory, every step.

This page builds the systems problems from first principles, then shows how the two most important open-source frameworks — Hugging Face's TRL and ByteDance's verl — solve them with nearly opposite architectures. Grounded in both codebases as of September 2026.

1 · One RL step, three different workloads

Every online RL step (PPO, GRPO, RLOO — the family doesn't matter) does four things: generate rollouts from the current policy, score them (reward + reference logprobs), learn (the gradient update), and sync the new weights back into whatever generated. The problem: these want different engines.

  • Generate is autoregressive decoding — memory-bandwidth-bound, KV-cache-hungry, 10–50× faster on a serving engine (vLLM/SGLang) than on model.generate() inside a training framework. For reasoning models it's usually more than half of wall-clock.
  • Score is prefill-only forwards through frozen models — cheap compute, more resident models.
  • Learn wants sharded optimizer state, activation checkpointing, fast backward — a training framework.

Where do the bubbles go? Watch two GPU pools over two RL steps. Colocation time-shares one pool; disaggregation splits pools and idles them; going one-step-off fills the bubbles at the price of staleness.

So the first structural fact: the best tool for generation and the best tool for training are different programs, with different memory layouts of the same weights. Nearly everything downstream is about resolving that tension.

2 · The four-model problem

SFT holds one model. Online RL can hold four: the policy (trained — needs gradients + optimizer), a frozen reference (KL anchor), a frozen reward model, and PPO's critic (trained too — its own optimizer state). Play with the ledger:

bf16 weights = 2 bytes/param; full-param training adds ~2 (grads) + ~12 (fp32 Adam m, v + master) ≈ the classic 16 bytes/param. Activations and KV cache come on top. Sharding (ZeRO/FSDP) spreads this over GPUs — it doesn't shrink it.

Flip between the two presets and you get the story of 2024→2026 RL infrastructure: the systematic elimination of resident models.

  • GRPO deleted the critic. Group-normalized rewards replace the learned value baseline. Discussed as an algorithmic insight; it's equally a systems win — it removes half the trainable memory of PPO.
  • Verifiable rewards deleted the reward model. For math/code, a regex extractor or a unit-test run is the reward, on CPU.
  • Two tricks deleted the reference model. Train with LoRA and the base-with-adapters-off is the reference (both frameworks exploit this); or set KL to zero and control drift with clipping + entropy monitoring.

3 · The two-copies problem

You can't eliminate the big one: the policy exists twice — sharded for training, laid out tensor-parallel for inference. Three ways to reconcile:

  • A — Colocate & time-share. Same GPUs flip engines: training state offloads, vLLM wakes; then vLLM sleeps, training state returns. Max utilization for synchronous RL; a resharding dance every step.
  • B — Disaggregate. Serving engine on its own GPUs; trainer ships prompts out and weights over. Cleaner memory, natural for async — but pools idle unless you break synchrony.
  • C — One engine. Use the trainer's generate(). Debug only.

The tax for two copies is weight sync — every step, new weights into the sampler. TRL's colocate sync is disarmingly direct:

# trl/generation/vllm_generation.py
for name, param in self._iter_named_params():
    self.llm.llm_engine.model_executor.driver_worker \
        .model_runner.model.load_weights([(name, param)])

Five attributes deep into vLLM internals: zero serialization, maximum fragility (TRL has shipped hotfixes for exactly this path). In server mode TRL is more principled — the trainer joins an NCCL communicator as rank 0 with the remote vLLM workers and broadcasts tensors; HTTP only carries metadata.

Details that matter at scale: the FSDP gather is lazy (DTensor full_tensor() all-gathers per tensor as the transfer consumes it — the full model never materializes); the transfer is bucketed (fixed 2–4 GB CUDA-IPC buffer over ZMQ with acks); and a delta_sharded mode ships only changed shards for disaggregated setups. If you remember one thing: weight sync is not an implementation detail — at 70B+ it's a first-order cost, and it's where RL frameworks differ most.

The subtle one: your two engines disagree about logprobs. vLLM's kernels, batching, and precision produce numerically different logprobs than your FSDP forward over the same tokens. Feed vLLM's numbers into the PPO ratio as πold and you've corrupted the ratio — it presents as slow, mysterious divergence. Both frameworks recompute old logprobs under the training engine (verl makes it a named pipeline stage), and both offer explicit importance-sampling correction as the cheaper opt-out (TRL: four vllm_importance_sampling_modes; verl: bypass_mode).

War story: TRL's first async GRPO ran generation in a thread and died of GIL contention + NCCL timeouts. The rewrite moved rollouts to a separate process.

5 · Rewards, references, and KL

Rewards, in increasing hosting cost: rule-based verifiers on CPU (2025's default for math/code — sandbox the code execution, and watch the verifier become the straggler; verl ships a 64-worker process-pool reward manager with timeouts) → reward model colocated on training GPUs (TRL's model) → RM on its own pool (one config line in verl) → remote RM service. Multi-reward is the norm, and normalization order matters: z-score each reward within the group before summing, or a high-variance reward silently dominates.

Reference model decision tree, encoded by both frameworks: KL coefficient zero → don't load one. Training LoRA → adapters-off is the reference (TRL literally keeps a second frozen adapter named "ref" and switches). Full-param with KL → pay for the frozen copy, CPU-offload it (it's forward-only).

The KL estimator matters more than it looks. With d = logπref − logπ, the three candidates: k1 = −d (unbiased, high variance, can go negative), k2 = d²/2, and k3 = ed − d − 1 (low variance, always ≥ 0). Both frameworks default to k3. Drag d:

Also non-equivalent: KL in the reward (classic RLHF — shapes advantages through the return) vs KL in the loss (GRPO — a direct gradient penalty). verl exposes both as config; TRL's GRPO uses in-loss.

6 · Two architectures, one problem

TRL — RL as a Trainer subclass

GRPOTrainer inherits from transformers.Trainer. That buys the whole HF ecosystem for free — accumulation, mixed precision, DeepSpeed/FSDP, checkpointing — and fixes the architecture: N identical data-parallel ranks, everything inlined into one training loop. No roles, no placement, no controller. Generation amortizes via a buffer (one call feeds steps_per_generation × num_iterations steps), and the step is strictly generate → train → sync — utilization sawtooths.

Its superpower is algorithmic surface area: a new algorithm is an elif in the loss —

# the loss_type ladder, late 2026:
grpo · dapo · dr_grpo · bnpo · cispo · sapo · vespo · luspo
# + DAPO's epsilon_high, delta-clamp, 5 loss-normalization
#   conventions as orthogonal config knobs

Papers land in days. The price: a ~3,500-line trainer where 8 loss types × 3 generation backends × 3 ref strategies × 4 IS modes all interact.

verl — RL as a dataflow, placement as configuration

verl (the HybridFlow paper productionized) makes RL a distributed dataflow: a single-controller driver owns the loop, and it reads like pseudocode —

batch = self._compute_old_log_prob(batch)   # fans out to Ray workers
batch = self._compute_ref_log_prob(batch)   # fans out to Ray workers
batch = self._compute_advantage(batch)      # on the driver, pluggable
batch = self._update_actor(batch)           # fans out to Ray workers

Each call looks local but fans out to a Ray worker group running SPMD internally (FSDP/Megatron training, vLLM/SGLang rollout). Worker methods declare how they distribute via @register(dispatch_mode=…); roles (actor, rollout, ref, critic, RM) map to GPU pools in config — colocating or dedicating GPUs per role is a config edit, not a refactor. Algorithms are registries, not subclasses: 14 advantage estimators, 13 policy losses, each a decorated ~50-line function; GRPO vs PPO is one config line. Async is first-class: three trainer modes, a staleness-tagged replay buffer, partial rollouts, an agent loop for multi-turn tool use.

The costs are what you'd predict: a vast Hydra config surface, silent Ray × NCCL × vLLM hangs as the top community complaint, OOM in the resharding path, and a version matrix that needs its own CI.

Convergent evolution. From opposite starting points, both frameworks independently arrived at: vLLM sleep/wake colocation with a starved KV budget (~0.3 vs the serving default 0.9) · recomputing old logprobs under the training engine · the LoRA-adapters-off free reference · k3 as default KL estimator · token- vs sequence-level IS switches (GSPO) · DAPO's tricks as config flags. When two systems with opposite control planes converge on the same six mechanisms, those aren't framework quirks — they're the invariants of the problem.

7 · Which one, when

TRL — 1–8 GPUs, LoRA, iterating on losses/reward shaping weekly, HF-native stack. Unmatched algorithm coverage and time-to-first-run; PEFT integration is genuinely first-class.
verl — 32B+, multi-node, MoE via Megatron, async or agentic rollouts, or when GPU utilization is the number your infra bill answers to. Budget real time for Ray debugging and config archaeology.
The honest middle — prototype in TRL, graduate to verl when scale demands it. The concepts transfer almost one-to-one: both are answering the same exam paper.
