LiveKit Agents: the architecture map

Added 2026-09-05

Why does LiveKit's agent framework feel so clean for voice? Because it splits the problem into two planes, makes every pipeline stage an async stream with the same shape, and treats turn-taking as a first-class ML problem instead of a VAD timeout. This page maps the core primitives, the model-swap trick, the turn-taking machinery, and LiveKit's own models (EOT, BVC) — with knobs you can play with.

1 · The big picture: two planes, one trick

LiveKit is two decoupled planes. The media plane is an open-source (Apache 2.0, Go) SFU — a WebRTC media server you can self-host, or use as LiveKit Cloud's global edge network. The agent plane is the Python framework (livekit/agents).

The one trick that buys all the cleanliness: your agent is just another participant in the room. Jitter buffers, codecs, reconnection, global routing — all of it is the SFU's problem. The framework only has to solve what happens between "audio frames in" and "audio frames out."

The EOT dial: probability → patience

The endpointing delay scales with what the EOT model believes (defaults: min_delay 0.5s, max_delay 3.0s). Drag the model's confidence:

High confidence → respond fast (snappy). Low confidence → hold on, the user is probably mid-thought (no interruption). Curve here is illustrative; DynamicEndpointing additionally adapts to each speaker's real pause rhythm with a moving average.

Also in the box: an ML interruption classifier that tells real barge-ins from backchannels ("uh-huh", "yeah") so the agent doesn't stop talking every time you nod audibly — with plain-VAD fallback and false-interruption resume.

5 · Latency simulator: why preemptive generation exists

After the user stops speaking, the reply latency is a chain: STT finalizes the transcript, the endpointing wait confirms the turn, the LLM produces its first token, TTS produces first audio. LiveKit's preemptive generation (on by default) starts the LLM speculatively during the endpointing wait, on STT's PREFLIGHT_TRANSCRIPT — and throws the result away if the user keeps talking. Simplified sequential model. If the user resumes speaking, the speculative generation is discarded (bounded retries per turn). The same idea extends to preemptive TTS.

The other latency weapons: pre-warmed job processes (models loaded, connections open before a user joins), LLM.prewarm() for DNS/TLS, local ONNX EOT on CPU in a separate inference process, and dynamic endpointing that learns each speaker's pause rhythm.

Why is the EOT model text-only? (and why that's clever)

It piggybacks on work already done: STT is already producing a live transcript, so the EOT model gets rich semantic context (the last 6 turns through a chat template) for free, and a ~135M model quantized to int8 runs in tens of milliseconds on CPU — no GPU in the serving path. The trade-off: it can't hear prosody (rising intonation, trailing-off), which is what the audio-capable cloud v1 variant adds.

Why does BVC run server-side, before VAD/STT?

Because the failure mode of background voices isn't annoyance — it's false turns. A TV voice in the background trips VAD, pollutes the transcript, and makes the agent respond to someone who isn't there. Scrubbing the audio before the VAD/STT stage kills the problem at the source instead of patching it downstream.

The business-model read

The transport is Apache 2.0; the intelligence is the funnel. EOT weights are open but licensed for use only inside LiveKit Agents; BVC needs Cloud credentials even when the binary runs on your box; and LiveKit Inference (Oct 2025) is a hosted gateway — one LiveKit API key for Deepgram / OpenAI / Cartesia / ElevenLabs etc., billed on the Cloud invoice (inference.LLM(model="gpt-4o") instead of provider SDKs). Open transport, proprietary intelligence.

7 · Deployment: workers, jobs, and one process per session

Job flow:

1 · Worker opens an outbound WebSocket to the LiveKit server and registers (reports load).
2 · A user joins a room → server dispatches a JobRequest to an available worker.
3 · The worker's ProcPool hands the job to a pre-warmed subprocess.
4 · Your entrypoint runs: build an AgentSession, session.start(room, agent).
5 · The session joins the room as a participant; audio flows.

Why one process per session?

Voice latency is a tail-latency problem. A GIL stall from another session's tool call, or a memory spike from a model load, becomes an audible dropout. Process isolation makes sessions blast-proof against each other, and the pre-warm hook (prewarm_fnc) hides model-loading and connection setup from the first turn. Heavy local inference (the EOT ONNX model) runs in a separate inference process shared over IPC, so it never blocks an audio loop. Deploy anywhere — it's just a Python process — or use LiveKit Cloud Agents managed compute.

8 · Why the abstraction is clean — the checklist

1. Async iterables all the way down. Frames, speech events, chat chunks, synthesized audio — every stage streams; composition is just async generators.

2. One stream lifecycle. Every .stream() pushes input via a channel and iterates output; the framework owns retries + metrics, plugins own provider logic.

3. Named override points, not middleware. Override stt_node / llm_node / tts_node on your Agent and wrap the default — no ordering hell.

4. Capability objects. STTCapabilities / RealtimeCapabilities let the framework adapt per provider (auto stream-adapters, server vs local turn detection) instead of dumbing the interface down.

5. Fallback adapters. N providers behind one interface with automatic failover — the rest of the framework can't tell.

6. Three-state config. NOT_GIVEN ≠ None: omitted means inherit (agent → session → auto), None means explicitly off.
