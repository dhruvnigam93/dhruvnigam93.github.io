Binary Search, Reframed

Added 2026-08-23

You keep writing if mid == 0 guards and getting infinite loops. The fix isn’t memorizing a template — it’s one reframe that makes the template fall out, corner cases already handled.

The reframe: binary search doesn’t “find a value in a sorted array.” It finds where a boolean test P(i) flips from False to True.

↑ it flips exactly once. Find the first T. That’s the whole game.

Every binary search is this — even the ones that don’t look like it:

Once you see which region still contains the flip, you discard the other half. You never classify a single element — that’s why mid-1 and the mid==0 guard disappear.

See it: the predicate lens

Step through the search. Watch the window shrink — the answer is always inside it (that’s the invariant), so the last cell standing is the answer, no special-casing. Dimmed cells are discarded: the answer provably can’t be there.

Try to break it: type 5 (a single element) into the array box. Most hand-rolled peak-finders crash here on nums[mid+1]. This one returns 0 and never enters the loop — the loop shape guarantees safety, no guard needed. (Principle 4.)

Why the corner cases vanish

01

Regions, not elements

Each step asks one thing: is the answer in [left, mid] or [mid+1, right]? One comparison discards one half. Classifying mid (“is this the peak?”) needs three — and drags in both neighbours and the ends.

02

Hold the invariant

Keep the answer always inside [left, right]. Then when the window shrinks to one cell, that cell is the answer — automatically. This is why you write right = mid (not mid-1) when mid could still be it: discarding a live candidate breaks the invariant.

03

Match the triad

Loop condition + update rule + return value are one set. Locating a guaranteed boundary → while left < right, right=mid / left=mid+1, return left. Searching a maybe-absent value → while left ≤ right, ±1 moves, return -1. Mixing rows is where your bugs live.

04

Safety is structural

With left < right, mid = (left+right)//2 always gives mid < right — so mid+1 is always in bounds. That theorem is what lets you delete if mid == len-1. Craving a boundary guard = wrong frame.

05

Prove progress on [a, b]

left = mid + 1 always advances. right = mid advances only when mid < right — which the strict loop guarantees. The two-element case is where infinite loops and off-by-ones hide. Trace it; if it terminates there, it terminates everywhere.

06

Not even about arrays

feasible(x) over a value range is the same shape: F…F T…T, find the first True. “Min days to ship”, “smallest divisor”, √n — all binary search once you name the monotonic predicate.

Feel the triad — mix it and break it

Same goal every time: find the first i with nums[i] ≥ 5 in [1, 3, 4, 6, 8, 9] (answer: index 3). We fix right = mid and let you pick the other two knobs. Only one combination terminates and is correct.

These are exactly the two mistakes that cost an hour on #33: left = mid with no +1 (no progress → infinite loop), and ≤ paired with a non-shrinking move. The template doesn’t hide these cases — it makes them impossible to write.

The recipe (write this, every time)

Tap each step as you internalize it.

  1. Name the monotonic predicate P(i) that flips False→True. If you can’t, it isn’t binary search.
  2. Set left, right to the full inclusive range of candidate positions.
  3. Pick the triad row. Locating a boundary → while left < right, return left.
  4. One comparison at mid → right = mid (answer at/left) or left = mid + 1 (answer strictly right).
  5. Write zero boundary guards. Wanting one means your predicate is wrong.
  6. Trace [a, b]. Terminates correctly there → you’re done.
Apply it cold to #162 Find Peak

1. Predicate: P(i) = nums[i] > nums[i+1] — are we on the down-slope? False on the way up, True from the peak onward. Flips once → binary-searchable.

2. Range: left, right = 0, n-1.

3. Triad: locating a guaranteed peak → strict loop, return left.

4. One comparison: P(mid) True → peak at/left → right = mid; else left = mid + 1.

5. Guards: none. mid < right makes mid+1 always valid.

The code isn’t memorized — it fell out of the recipe:

left, right = 0, len(nums) - 1
while left < right:
    mid = (left + right) // 2
    if nums[mid] > nums[mid + 1]:   # down-slope
        right = mid                  # peak at mid or left
    else:
        left = mid + 1               # peak strictly right
return left                          # left == right -> a peak

6. Trace [2, 1]: mid=0, 2>1 → right=0 → return 0. Trace [1, 2]: mid=0, 1>2 false → left=1 → return 1. Both terminate, both correct. Ship it.

The deeper point: the template isn’t a thing to recall — it’s what you get when you commit to the frame first. Predicate → invariant → triad, before the first line of the loop. Grow branches to patch the current element and you rebuild the corner cases by hand, every time.
