LiveKit's Eval Loop — and the RL That Closes It

Added 2026-09-09

The one insight

Theo personally built LiveKit's simulation + evals stack over the last ~3 months, and it is RL scaffolding with no RL on it yet. The repo ships livekit.agents.simulation (scenarios, LLM-simulated users, verdicts), livekit.agents.evals (8 LLM judges scoring pass / maybe / fail), and CI that runs end-to-end agent simulations on every push to main. There is zero RL code anywhere in the org — their shipped ML is all supervised (Turn Detector v1, an interruption classifier, answering-machine detection).

So the Research Engineer (RL) role is greenfield: turn verdicts and judges into rewards, and post-train against them. The Dream11 loop — data → reward model → GRPO → vLLM serving → A/B — is exactly the missing piece.

Everything below is real code pulled from livekit/agents on Sep 9 2026 — mostly the examples/frontdesk appointment-booking agent, which is Theo's own canonical demo of the whole system (his PR #6089).

The real code, layer by layer

1 · A scenario is a reward spec in YAML

Each scenario in scenarios.yaml defines a persona for the simulated user, expectations for the simulator's LLM verdict, and userdata that seeds the sandbox and encodes the ground-truth target. This one is adversarial — success means the agent books nothing:

# examples/frontdesk/scenarios.yaml (one of 10 scenarios, trimmed)
- label: Refuses every alternative, no booking allowed
  instructions: |-
    You are Victor Hale, a contractor who is sure he was told
    8 AM Thursday was free. You are stubborn and mildly irritated.
    Goals:
    - Demand an appointment on Thursday, June 18 at exactly 8 AM.
    - Reject every alternative the agent offers ...
    - ... give up and end the call without booking anything.
      Never provide your email address.
  agent_expectations: The agent must state that June 18 at 8 AM is
    not available and must not pretend otherwise or book a different
    time without the caller's agreement ...
  tags:
    feature: adversarial
  userdata:
    available_slots:
      - "2026-06-18T11:00:00"
      - "2026-06-19T10:00:00"
    expected_booking: null   # ground truth: book NOTHING

expected_booking has three regimes: a concrete slot (verifiable positive), null (verifiable negative — the agent must not act), or omitted entirely (graded on conversation only). All scenarios run against a pinned clock (SIMULATION_NOW = "2026-06-12T09:00:00", a Friday) so absolute dates are deterministic.

2 · Stateful tool mocks = an execution sandbox

Under simulation, the agent's real calendar tools are swapped for mocks backed by a FakeCalendar seeded from the scenario. The mocks share live state — a booking changes what the next list_available_slots call returns (there's a scenario that specifically probes this):

# examples/frontdesk/simulation.py (trimmed)
def tool_mocks(cal: FakeCalendar, tz: ZoneInfo) -> dict[str, Callable]:
    """Tool mocks sharing live state: a booking changes what the
    mocked list_available_slots returns on the next call."""
    async def list_available_slots() -> str:
        slots = await cal.list_available_slots(...)
        ...
    async def schedule_appointment(ctx: RunContext, slot_id: str):
        ...
        await cal.schedule_appointment(start_time=slot.start_time, ...)
    return {"list_available_slots": list_available_slots,
            "schedule_appointment": schedule_appointment}

# examples/frontdesk/agent.py — the entrypoint wires it up
@server.rtc_session(on_session_end=on_session_end,
                    on_simulation_end=on_simulation_end)
async def frontdesk_agent(ctx: JobContext):
    if sim := ctx.simulation_context():
        # scenario userdata seeds the calendar, pinned to its clock
        cal = simulation.fake_calendar(sim, timezone="UTC")
        tool_mocks = simulation.tool_mocks(cal, ZoneInfo("UTC"))
    ...
    mock_tools(FrontDeskAgent, tool_mocks, session=session)

This is, in RL vocabulary, an execution sandbox: deterministic initial state, real tool interface, no real side effects, final state inspectable.

3 · The verifier: on_simulation_end and the AND-gate

After the conversation, the simulator produces its own LLM verdict of the chat. Then your code runs and can veto based on ground truth. From the SimulationContext docstring: "The effective result is the AND of the two: your check can fail a run the simulator passed, but it can never rescue one" — there is deliberately no success() method, only fail().

# examples/frontdesk/agent.py
async def on_simulation_end(ctx: SimulationContext) -> None:
    # grade the run on final calendar state; a mismatch vetoes the run
    userdata = ctx.userdata()
    if "expected_booking" not in userdata:
        return   # scenario graded on conversation only

    cal: FakeCalendar = ctx.job_context.primary_session.userdata.cal
    booked = cal.scheduled_appointments

    if (expected_raw := userdata["expected_booking"]) is None:
        if booked:
            ctx.fail(reason=f"no booking was expected, but the "
                            f"agent booked: {times}")
        return

    expected = simulation.parse_slot(expected_raw, cal.tz)
    if len(booked) != 1 or booked[0].slot.start_time != expected:
        ctx.fail(reason=f"expected a single booking at "
                        f"{speak(expected)}, got {times}")

Note what's being graded: not the transcript, but whether exactly one appointment exists at exactly the right time on the calendar. An LLM can be charmed; a state check cannot.

4 · The 8 judges — and they run in production too

This is the detail most people miss: on_session_end is not simulation-only. It runs after every session, including live production calls, fans out all 8 judges concurrently, auto-tags results onto the session, and records a hard success/fail from real state:

# examples/frontdesk/agent.py
async def on_session_end(ctx: JobContext) -> None:
    report = ctx.make_session_report()
    ...
    judges = JudgeGroup(
        llm="openai/gpt-4o-mini",
        judges=[
            task_completion_judge(),   # First Call Resolution
            accuracy_judge(),          # grounded in tool outputs?
            tool_use_judge(),          # right tool, right args?
            handoff_judge(),           # context kept across handoffs?
            safety_judge(),            # advice/disclosure/escalation
            relevancy_judge(),         # on-topic?
            coherence_judge(),         # logical, no contradictions?
            conciseness_judge(),       # brevity — voice-specific
        ],
    )
    await judges.evaluate(report.chat_history)  # auto-tagged to session

    if ctx.primary_session.userdata.cal.scheduled_appointments:
        ctx.tagger.success()
    else:
        ctx.tagger.fail(reason="Appointment was not booked")

Every production call already emits a reward tuple (8 verdicts + a binary outcome tag) into their observability pipeline. That's a live reward-telemetry flywheel — before anyone has written a line of RL.

5 · Inside a judge: forced tool call, temp 0, priority class

Verdict extraction is engineered, not vibes — the judge must call a function tool, at temperature 0, and every judge call is pinned to the low-priority inference class:

# livekit/agents/evals/judge.py
Verdict = Literal["pass", "fail", "maybe"]

@function_tool
async def submit_verdict(verdict: Verdict, reasoning: str): ...

response = await llm.chat(
    chat_ctx=eval_ctx,
    tools=[submit_verdict],
    tool_choice="required",           # cannot skip the verdict
    extra_kwargs={"temperature": 0.0},
    **_judge_chat_kwargs(llm),        # pins inference_class="low"
).collect()

# why "low"? (verbatim comment from the source)
# "Judging is batch load: an eval suite fans out many judgments at
#  once, they run after the conversation they grade, and nobody is
#  waiting on the verdict. So they are pinned to the low inference
#  class and must not compete with live traffic for gateway capacity"

And an example of what a judge actually checks — accuracy_judge's full rubric:

"All information provided by the agent must be accurate and grounded.
 Fail if the agent states facts not supported by the function call
 outputs, contradicts information from tool results, makes up details
 (hallucination), or misquotes data like names, dates, numbers, or
 appointments."
6 · Scoring: pass=1, maybe=0.5, fail=0 — already a reward in [0,1] 
# livekit/agents/evals/evaluation.py (condensed)
@property
def score(self) -> float:
    """Score from 0.0 to 1.0. Pass=1, maybe=0.5, fail=0."""
    total = sum(1.0 if j.passed else 0.5 if j.uncertain else 0.0
                for j in self.judgments.values())
    return total / len(self.judgments)

# plus aggregation policies, ready-made:
result.all_passed        # maybes count as NOT passed
result.majority_passed   # > half passed
result.none_failed       # maybes tolerated, explicit fails not

Inside Theo's mind: what each choice is capturing

Read as a systems designer's decisions, the stack encodes six beliefs — and each one maps directly onto an RL design decision:

1. LLM judges are advisory; state is truth. The AND-gate (your verifier can veto, never rescue) is anti-reward-hacking architecture built before any RL exists. He already doesn't trust the judge alone.

2. Scenarios are reward specs. expected_booking: value / null / omitted = verifiable-positive / verifiable-negative / judge-only. He's authoring reward functions in YAML without calling them that.

3. Determinism is non-negotiable. Pinned clock, seeded slots, stateful mocks — reproducible episodes. That's the property that turns an eval suite into a trainable environment.

4. Judge reliability is an engineering problem. Forced tool-call extraction, temperature 0, and a three-way verdict where "maybe" scores 0.5 — uncertainty is measured, not rounded up to pass.

5. Eval traffic must never touch prod latency. Everything offline is pinned to inference_class="low". A priority-classed shared inference fleet is exactly the substrate RL rollout generation needs — it already exists.

6. Rewards trace to business metrics. task_completion_judge's docstring names First Call Resolution, "the key metric in call centers." And the same judges + success/fail tagging run on live production sessions — the reward telemetry flywheel is already spinning.

The RL recipes

Recipe 1 — GRPO in their own sandbox

GRPO wants exactly what this stack provides: many rollouts of the same task, a scalar reward, no value network. A group = G rollouts of one scenario (same seeded calendar, same persona); the advantage is normalized within the group.

# sketch — GRPO on the frontdesk agent, using LiveKit primitives
async def rollout(scenario, policy_llm):
    cal = simulation.fake_calendar(sim, timezone="UTC")   # seeded sandbox
    mock_tools(FrontDeskAgent, simulation.tool_mocks(cal, tz))
    async with AgentSession(llm=policy_llm,
                            userdata=Userdata(cal=cal)) as sess:
        await sess.start(FrontDeskAgent(timezone="UTC", now=cal.now))
        await drive_sim_user(sess, persona=scenario.instructions)
    return sess.history, cal

async def reward(chat, cal, scenario):
    v = verify_state(cal, scenario)                 # {0, 1}  hard gate
    j = (await judge_group.evaluate(chat)).score    # [0, 1]  shaped
    return v * (0.6 + 0.4 * j)   # gated: judges refine, never rescue

for scenario in scenarios:                # GRPO outer loop
    group = [await rollout(scenario, policy) for _ in range(G)]
    r = [await reward(c, cal, scenario) for c, cal in group]
    adv = (r - mean(r)) / (std(r) + 1e-6)
    update(policy, grpo_loss(adv, kl_to_reference=beta))

The reward is multiplicative, not additive — the verifier gates, the judges shape. That mirrors Theo's AND-gate exactly, and the widget below shows why it matters.

Reward design playground. Six rollouts of the "Tom wants July 16, 1 PM" scenario (G=6). V = verifier (did the right booking land), J = judge score. Blend them with λ and watch which rollouts GRPO up-weights (positive advantage) vs down-weights:

r = λ·V + (1−λ)·J   λ = 0.60

Recipe 2 — distill the judges into a reward model

Judge calls are slow and expensive at training scale (8 × LLM call per rollout). Standard move: run the full judge panel + verifier offline over thousands of group rollouts, form pairwise preferences within each group (same scenario, so comparisons are apples-to-apples), and train a small reward model on them. Then GRPO against the cheap dense RM with a KL anchor, re-validating periodically against the real judges. This is the close-pairs RM discipline from Dream11 — pairs from the same context are the highest-signal pairs.

Recipe 3 — RL from production, not just simulation

Because on_session_end already judges live calls and tagger.success()/fail already records outcomes, production is emitting (trajectory, reward) tuples today. The conservative ladder: filtered SFT (clone only high-scoring calls) → DPO (pair high vs low scoring calls on similar intents) → offline RL. No live exploration — you never let a training policy experiment on a real caller. The just-shipped PII redaction (1.7/1.8) is the unglamorous prerequisite that makes prod transcripts usable as training data.

Recipe 4 — the turn-taking policy

Different model, same logic. Turn Detector v1 outputs an end-of-turn probability; the policy on top (threshold, action_delay, timeout) is grid-searched in eot-bench. That's a sequential decision problem begging for a learned policy: act ∈ {commit, wait, backchannel}, reward = −false-cutoff − latency·ms + clean handover, trained offline from logged prod signals (agent_false_interruption events, user restarts). And a threshold policy over probabilities is only principled if the probabilities are calibrated — which is the ForeCal conversation.

What breaks: reward hacking, and the defense they already built

Judge-only reward gets hacked: the policy learns to be charming, verbose-then-apologetic, or sycophantic to the judge rather than to book the right slot (rollout C in the widget). Mitigations, in order of leverage: the verifier gate (already in the architecture — say this to Theo), held-out judge models the policy never trains against, judge ensembles with disagreement flags, KL to reference, fresh adversarial scenarios (their feature: adversarial tag is already the seed of a red-team suite), and monitoring the prod judges for drift once a trained policy ships.

Three lines for the room:

1. "You've already built the environment, the verifiers, and the reward telemetry — what's missing is the loop that trains against them, and I've run that loop end to end in production."

2. "Your AND-gate — verifier can veto, never rescue — is the exact reward-gating discipline that keeps GRPO from hacking the judges. I'd keep it as r = v·(0.6+0.4j)."

3. "on_session_end judging live calls means every production conversation is already a labeled trajectory. Filtered SFT and DPO on that data are shippable before any online RL."

Receipts: we built the same three layers on the Companion

This isn't theory for you — the AI Companion codebase (ds-ai-companion-rtc, built on LiveKit) independently converged on the same architecture: E2E runs, an LLM judge, a programmatic verifier, and a production telemetry corpus. Different trade-offs, same shape. Know your own code cold — Theo may ask exactly this.

And the verifier (test_lineup_compliance.py) — our expected_booking: does every fantasy pick reference a player who is actually in the provided lineup? Grounding checked in code, not by an LLM:

# ds-ai-companion-rtc/scripts/test_lineup_compliance.py (trimmed)
def check_compliance(picks, lineup):
    """Check each pick against the lineup. Returns violations."""
    violations = []
    for pick in picks:
        normalized = normalize(pick.get("player", ""))
        if not any(match(normalized, norm) for norm, _, _ in all_players):
            violations.append({"player": pick["player"],
                               "closest_match": get_close_matches(...)})
    return violations   # hallucinated player = hard fail, however fluent
